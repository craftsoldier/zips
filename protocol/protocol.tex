% Quattrocento is beautiful but doesn't have an italic face. So for emphasis, we
% scale New Century Schoolbook italic to fit in with slanted Quattrocento and match
% its x height. (This has the side effect of making all emphasized text into boxes,
% so it won't linebreak, which has pluses and minuses.)
%
% XeTeX and LuaLaTeX require the \fontencoding{T1}:
% <https://tex.stackexchange.com/a/426300/78411>
%
% New Century Schoolbook italic bold is too wide, and there is no math sans italic
% font, so we override \strongvartype to \strongvaritalictype, and \mathsansvartype
% to \mathsansitalictype to provide better alternatives while in \emph.
\newcommand{\schoolbook}[1]{{\fontencoding{T1}\fontfamily{pnc}\selectfont{#1}}}
\newcommand{\schoolbookitalic}[1]{\scalebox{1.02}[0.999]{\schoolbook{#1}}}

\normalsize \noindent \textbf{Abstract.}
\defining{\Zcash} is a cryptocurrency originally built on \Bitcoin, keeping its transparent
payments and adding privacy-preserving \emph{shielded} payments, which hide the sender,
recipient and amount of transactions that stay within a shielded pool and are proved valid
with zero-knowledge proofs.

\lsection{Introduction}{introduction}
\phantomsection\label{overview}

\Zcash builds on the \Zerocash payment scheme \cite{BCGGMTV2014}, with security fixes and
improvements to performance and functionality, and proves its shielded payments with
\zeroKnowledgeSuccinctNoninteractiveArgumentsOfKnowledge, which over the network's history
have been carried by three shielded protocols: \Sprout, the protocol from launch until the
Sapling upgrade; \Sapling, introduced by the network upgrade of the same name and used for
the Sapling pool; and \Orchard, used for both the Orchard pool and the Ironwood pool.

Value in \Zcash sits in six pools, the transparent, Sprout, Sapling, Orchard, Ironwood and
deferred development fund pools, and transparent value moves essentially as in \Bitcoin,
with addresses and amounts visible on the block chain. Shielded value is carried instead by
notes, each of which specifies an amount and indirectly the shielded payment address the
note was sent to, and notes sent to an address can be spent with the spending key for the
address, yet the note itself never appears on the block chain in readable form, since
anyone reading the chain would then learn the amount and the address.

For each note, the block chain records a note commitment, which works like a sealed
envelope hiding the note while fixing the contents so nobody can change them later. Each
commitment takes a fixed place in a tree of note commitments, and the owner can later prove
a note sits in the tree without opening the envelope.

A commitment alone cannot mark a note as spent, since pointing at the commitment would show
everyone which note was spent, so each note also has a nullifier, which only the owner's
keys can compute and nobody else can connect to the commitment. Spending a note reveals the
nullifier, and every node keeps the nullifiers seen so far and rejects any transaction
revealing one already on the block chain, so a note stays unspent until the nullifier
appears and can never be spent twice.

A transaction can carry transparent inputs and outputs alongside shielded parts, which
spend notes and create new ones, and for each note spent the spender attaches a
zero-knowledge proof showing the commitment is somewhere in the tree, the nullifier belongs
to the same note and the spender holds the right key, without revealing which commitment is
meant. Signatures stop anyone else from altering the transaction, and every transaction
must balance, so no value is created out of nothing.

The recipient learns of a payment from a copy of the note the sender publishes encrypted to
the recipient's address, like a letter only the recipient can open, and the ciphertext
gives no hint of who the letter is for. The recipient's wallet scans the block chain to find
and decrypt the notes addressed to the recipient, and in Sapling, Orchard and Ironwood a
full viewing key sees incoming and outgoing notes without the power to spend, much like
read-only access to a bank account.

With no spend ever naming a commitment, a spent note cannot be linked to the transaction
which created the note, and to an observer the note could be any earlier note the observer
does not control or know to be spent. The guarantee covers fully shielded transactions
only, since the number of inputs and outputs, the timing and any amount moving between pools
remain visible.

\pagebreak
\lsection{Concepts}{concepts}
\phantomsection\label{addressesandkeys}\label{notes}\label{noteptconcept}\label{notecommitmentconcept}%
\label{nullifierconcept}\label{blockchain}\label{transactions}\label{joinsplit}\label{spendsandoutputs}%
\label{actions}\label{networks}

\textbf{Keys and addresses.} To receive a shielded payment, a user needs a shielded payment
address, which a wallet makes from a spending key together with a chain of weaker keys, each able
to make the keys below it but never the keys above. A full viewing key shows incoming and outgoing
payments, an incoming viewing key shows only incoming payments, and an address lets others pay the
user while showing nothing. Most wallets make \Sapling and \Orchard keys from one seed, as
\cite{ZIP-32} describes.

Payments to one address do not show on the block chain as payments to one user, not even to the
payers, but two payers who compare addresses can see the match. \Sprout gives one address to each
spending key, while \Sapling and \Orchard let one spending key make many rotating (diversified)
addresses, which share the same viewing keys, so a user can give each payer a different address and
scan the block chain once for all of them.

\textbf{Notes.} A note belongs to one shielded pool and records an amount in zatoshi, the address
the note was sent to, and random values for the note commitment and the nullifier. Each note goes
onto the block chain encrypted to the recipient, with a 512-byte memo for the sender and the
recipient to use as they agree, and each encrypted note starts with a version byte whose allowed
values depend on the pool and the block height.

From block 3,363,426 on Mainnet until the NU6.2 upgrade, no transaction could contain \Orchard
Actions. Since NU6.3, value can leave the Orchard pool but cannot go into the Orchard pool, and new
payments to \Orchard addresses go into the Ironwood pool, which uses the \Orchard protocol.

\textbf{Commitments and nullifiers.} When a transaction makes a note, the note commitment goes into
the note commitment tree of the note's pool, and when a transaction spends the note, a
zero-knowledge proof shows the note commitment is in the tree without showing which note
commitment belongs to the note. Spending the note puts the note's nullifier into the pool's
nullifier set, and a transaction is not valid if the nullifier is already in the set, so each note
can be spent only once. The nullifier comes from values in the note and from a key of the owner,
the spending key in \Sprout and the nullifier deriving key in \Sapling, \Orchard and Ironwood.

\textbf{The block chain.} Each node sees a tree of candidate blocks that starts at the genesis
block, and a path of valid blocks through the tree is a valid block chain, with block heights from
$0$ that nodes must support up to $2^{31} - 1$. A node follows the valid block chain with the most
total work, takes the block received first when two blocks tie, and may refuse to roll back more
than a fixed number of blocks, $100$ for zcashd and zebra.

A network upgrade is settled when there is social consensus on the block where the upgrade
activated, and software that holds Mainnet funds must follow a block chain that contains that block
for the most recent settled upgrade. Social consensus also decides which node software follows the
Mainnet rules, at present zebra from the Zcash Foundation and zcashd from the Zcash Open
Development Lab, and zcashd will not support the changes in NU6.3.

\textbf{Transactions and treestates.} Each transaction has a transaction ID, which block explorers,
other transactions and the block's Merkle tree use to refer to the transaction. In a transaction,
transparent inputs and shielded spends add value to a balance, transparent outputs and shielded
outputs take value from the balance, and the value that remains, which must not be negative, is
the fee for the miner.

Each shielded pool has a treestate, made of the note commitment tree and the nullifier set, which
passes from each transaction to the next transaction and from each block to the next block. A spend
refers to an anchor, the root of the note commitment tree at an earlier block, and proves the note
commitment is in the tree at that point.

\textbf{Shielded transfers.} A \Sprout JoinSplit spends up to two notes and makes up to two notes,
proves inside the proof that the values balance, and can use the result of an earlier JoinSplit in
the same transaction. \Sapling uses a separate Spend for each spent note and a separate Output for
each new note, each with a value commitment, and one binding signature proves the value commitments
of the whole transaction balance. \Orchard puts one optional spend and one optional output into
each Action, with one value commitment for the net value, and puts the proofs for all Actions of a
transaction together, and neither \Sapling nor \Orchard lets a transaction spend a note made in the
same transaction.

\textbf{Trees and nullifier sets.} The note commitment tree of each pool is a Merkle tree of fixed
depth that only grows, which shows value exists in the way the set of unspent outputs does in
\Bitcoin but does not prevent double spending, and no block may add more note commitments than the
tree can hold. Each node keeps one nullifier set for each pool, no nullifier may appear twice in a
valid block chain, and the nullifier sets of different pools stay separate even when two
nullifiers have the same bits.

\textbf{Block rewards.} Like \Bitcoin, \Zcash makes new currency with each block, and the block
subsidy goes to the miner and, for the first four years, to the Founders' Reward, or after that to
the developer funding streams. The coinbase transaction, the first transaction in each block,
collects the block subsidy and the fees of the other transactions, and chapter 7 gives the amounts.

\textbf{Testnet.} Testnet is a public test network next to Mainnet, with a TAZ token that has no
intended value, and Testnet usually activates each network upgrade before Mainnet to find errors in
the specification or the software, but the Testnet block chain can be rolled back at any time. On
both networks the smallest unit of currency is the zatoshi, and one ZEC or one TAZ is $10^8$
zatoshi.

\lsubsection{Cryptographic tools}{readabletools}
\phantomsection\label{abstractcommit}\label{abstractgroup}\label{abstractkdf}\label{abstractkeyagreement}\label{abstractprfs}\label{abstractprps}\label{abstractsig}\label{abstractsigmono}\label{abstractsigrerand}%

A public ledger lets every node check every payment by showing everything, and a shielded payment has to hide the same facts without losing the check. Zcash manages the trade with a small set of cryptographic tools, each described here by the guarantee the tool gives rather than by the algorithm behind the guarantee.

\textbf{Commitments.} A note has to go onto the block chain without being readable, and a commitment works like a sealed envelope, hiding the note while fixing the contents so nobody can change them later.

\textbf{Pseudo-random functions.} A spent note then needs a mark only the owner can compute and nobody can connect to the envelope. A pseudo-random function, a keyed hash whose outputs look random to anyone without the key, gives exactly such a mark, and a note's nullifier is one of these outputs under a key belonging to the owner.

\textbf{Zero-knowledge proofs.} The owner must still convince every node the hidden note exists and belongs to the owner. A zero-knowledge proof shows secret values pass a public list of checks while revealing nothing else about the values, and a correct proof always verifies, while nobody can feasibly prove a false claim.

\textbf{Signatures.} A proof on the block chain could be copied into another transaction, or altered by someone without the secret values into a proof about related values, and signatures over the whole transaction prevent both. Zcash uses two unusual kinds of signature, one whose key can be re-randomized for each spend and one whose keys can be added together.

\textbf{Value commitments.} Amounts are hidden too, yet a node must still check the value going into a transaction matches the value coming out. The value commitments of Sapling and Orchard can be added together without being opened, and a signature whose keys add in the same way shows the hidden amounts balance.

\textbf{Encryption.} The recipient has to learn what the note contains while nobody else does. Key agreement gives the sender and the recipient one shared secret, a key derivation function turns the secret into a key, and authenticated encryption seals the note, hiding both the contents and the address the note is for.

\textbf{Hash functions.} Nobody can feasibly find two inputs to a hash function with the same output, and hash functions build the tree of note commitments and give the fixed curve points behind commitments and addresses.

\lsubsection{Keys}{readablekeys}
\phantomsection\label{orchardkeycomponents}\label{saplingkeycomponents}\label{sproutkeycomponents}%

A wallet with one key for everything would put the power to spend at risk every time the wallet only needed to read or receive a payment. Zcash instead derives a chain of keys from one random spending key, and each step runs one way, so a weaker key can be handed out without exposing the keys above.

\textbf{Sapling.} The spending key gives three secrets, the spend authorizing key for approving spends, the nullifier private key for computing nullifiers and the outgoing viewing key for reading payments sent. The public halves $\mathit{ak}$ and $\mathit{nk}$ of the first two, together with the outgoing viewing key, form the full viewing key, and a hash of $\mathit{ak}$ and $\mathit{nk}$ gives the incoming viewing key, which finds and reads payments received.

\textbf{Orchard and Ironwood.} The keys keep the same roles, but the outgoing viewing key and a diversifier key come from the full viewing key rather than straight from the spending key. Wallets must derive Orchard keys exactly as specified, or the notes may not be recoverable through the recovery protocol of \cite{ZIP-2005} if attacks with quantum computers become practical.

\textbf{Sprout.} The spending key gives one paying key and one receiving key, and each spending key has exactly one address.

\textbf{Addresses.} A Sapling or Orchard address pairs a diversifier with a transmission key made from the diversifier and the incoming viewing key, so every new diversifier gives a new address. The addresses work like post-office boxes forwarding to one mailroom, where outsiders cannot tell which boxes belong together while the one incoming viewing key finds the mail sent to every box. Orchard makes each diversifier from a diversifier index, and wallets should not pick the index at random \cite{ZIP-32}.

\textbf{Failed derivations.} A derivation can now and then produce a value which is not a valid key, and the wallet then discards the spending key and starts again with a new one.

\lsubsection{Shielded parts of a transaction}{readabledescriptions}
\phantomsection\label{joinsplitdesc}\label{outputdesc}\label{spenddesc}%

Nodes cannot see a shielded transfer, so the transaction carries a description of the transfer instead, holding the public values the checks need and a proof the hidden values behind them are right. No description shows a note or a shielded address, every field must be a valid encoding, and every proof must verify.

\textbf{JoinSplits.} A Sprout JoinSplit spends two notes and creates two, and two public amounts move value in or out of the transparent side of the transaction, at most one of them non-zero. Since Canopy the amount moving into Sprout must be zero, which closes the Sprout pool to new value.

\textbf{Spends and Outputs.} Sapling gives each spent note a Spend, which carries a spend authorization signature over the whole transaction, and each new note an Output, which carries the encrypted note and no signature. The value commitment and the randomized key of a Spend, and the value commitment and the ephemeral key of an Output, must not be points of small order.

\textbf{Actions.} Orchard and Ironwood join one optional spend and one optional output into each Action, with one value commitment for the net value. Two flags for each pool say whether the Actions may spend and may create non-zero value, and from NU6.3 a third flag says whether a new note may go to a different address from the spent note. Every field of an Action must be a canonical encoding, and the randomized key must not be the identity point. The proof must verify under the verifying key of the circuit in force, and the circuit changed at NU6.2, to fix a flaw which could have let a transaction break the balance rule, and again at NU6.3.

\lsubsection{Sending notes and dummy notes}{readablesending}
\phantomsection\label{sproutdummynotes}%

A sender has the recipient's address and no private channel to the recipient, so the sender builds the whole note alone and puts everything the recipient needs on the block chain. The sender chooses fresh random values, computes the value commitment and the note commitment, encrypts the note to the recipient and makes the proof.

Since Canopy most of a note's random values come from one 32-byte seed, $\mathit{rseed}$, which travels inside the encrypted note so the recipient can rebuild the note exactly. In Orchard the new note's $\rho$ is the nullifier of the note spent in the same Action. The sender also adds a second, shorter ciphertext readable by an outgoing viewing key, which lets the sender read the payment again later, or readable by no key at all, which keeps the payment secret even if the sender's keys later leak.

Wallets should shuffle the order of spends and outputs to reveal less about the transaction. Since Canopy wallets must not send to Sprout addresses \cite{ZIP-211}.

\textbf{Dummy notes.} A transaction can still give away how many notes the sender really spends, and dummy notes hide the count. A dummy note is a note of zero value under a throwaway key, like a cheque made out for nothing, which fills a place in a transaction without moving money. JoinSplits use dummies to fill the fixed room for two notes in and two out, and Sapling and Orchard use dummy spends to hide the number of real spends. An Orchard Action with no real note to spend should spend a dummy note and take the dummy's nullifier as the new note's $\rho$. A dummy passes every check a real note passes except one, as the proof does not require a note of zero value to be in the tree.

\lsubsection{Merkle paths}{readablemerkle}

A spender has to show the spent note is one of the notes on the block chain without saying which one. Each pool keeps the pool's note commitments in a Merkle tree of fixed depth which only grows. A Merkle path lists the neighbouring hash at each level from one note commitment up to the root, so anyone holding the commitment and the path can recompute the root. The spender keeps the commitment and the path secret inside the proof, and the transaction names only the root, called the anchor, so nodes learn the note is in the tree but not where.

\lsubsection{Signatures and balance}{readablesigbalance}
\phantomsection\label{orchardbalance}\label{saplingbalance}\label{sighash}\label{spendauthsig}\label{sproutnonmalleability}%

Once the parts are built, nobody should be able to change the transaction, and every node must be able to check the hidden amounts balance. Each signature in a shielded transaction signs the SIGHASH, a hash of the whole transaction, computed for version 4 as \cite{ZIP-243} specifies, for version 5 as \cite{ZIP-244} specifies and for version 6 as \cite{ZIP-229} specifies. From NU5 the SIGHASH type must be one of the defined types in canonical form, and every transaction must name the consensus branch of the upgrade in force.

\textbf{Sprout.} Sprout signs each transaction with a throwaway key used once, and the proof ties the key to the owners of the spent notes through the value $h_{\mathsf{Sig}}$. Sprout also checks the balance inside the proof.

\textbf{Balance.} Sapling and Orchard check the balance outside the proof, with value commitments which can be added together. A commitment to a value $v$ with a random trapdoor $\mathit{rcv}$ is

\begin{center}$\mathit{cv} = v \cdot V + \mathit{rcv} \cdot R$\end{center}

for two fixed points V and R, so adding commitments adds the values and the trapdoors separately. A node adds the commitments of the spends, subtracts those of the outputs and subtracts the public amount the pool releases to the transparent side. In an honest transaction the values cancel and only a multiple of R remains, a public key whose private key, the sum of the trapdoors, only the builder of the transaction knows.

The builder signs the transaction with the private key, and the signature, called the binding signature, must verify under the public key each node computes from the commitments. If the values did not cancel, a valid signature would need one commitment opened to two different values, which the commitments rule out. Every value fits in 64 bits and a transaction holds only so many parts, so the sum cannot wrap round to zero either. Proving knowledge of the trapdoors also stops anyone copying an Output into another transaction, and Orchard and Ironwood work the same way, with one net value commitment per Action and one binding signature per pool.

\textbf{Spend authorization.} The binding signature shows the values balance but not the spender's right to spend them, and a separate spend authorization signature proves the spender holds the key of each spent note. Keeping the signature outside the proof lets a device with little memory or computing power, such as a hardware wallet, approve a spend without building the proof. A signature checked against the owner's own key would link every spend to the owner's address. The wallet instead shifts the key by a fresh random value for each spend and publishes the shifted key $\mathit{rk}$, the owner's key in a fresh disguise, and the proof shows $\mathit{rk}$ disguises the right key. A wallet may hand the proof to a helper, who then learns enough to see the owner's payments but still cannot spend.

\lsubsection{Nullifiers and pool balances}{readablenullifiers}
\phantomsection\label{rhoandnullifiers}%

A nullifier has to follow from the note alone, differ from the nullifier of every other note, and stay unlinkable to the note for anyone without the owner's key, even the sender. Each note therefore has a value $\rho$ no other note shares, which Sprout and Orchard notes carry inside the note and Sapling computes from the note commitment and the note's place in the tree. The nullifier is computed from $\rho$ under a key of the owner, the spending key in Sprout and the nullifier deriving key in Sapling and Orchard.

\textbf{Faerie Gold.} Without unique $\rho$ values a payer could send two notes with the same nullifier, both of which look valid to the recipient although only one can ever be spent, an attack named Faerie Gold. Orchard rules the attack out by setting each new note's $\rho$ to the nullifier of the note spent in the same Action, and since each nullifier appears on the chain at most once, every $\rho$ is unique.

\textbf{Pool balances.} Nullifiers protect each note, and pool balances protect the supply as a whole. Each chain value pool keeps a running balance of the value the pool has received minus the value paid out, and a block which would make any pool's balance negative is invalid. The rule works like a turnstile at the entrance of each pool, so a bug in a shielded pool could create false value inside the pool, but no more value could leave the pool than entered \cite{ZIP-209}. The total supply across all pools must never exceed 21 million ZEC, and from NU7 the balance the Network Sustainability Mechanism holds for reissue must also stay non-negative.

\lsubsection{What the proofs prove}{readableproofs}
\phantomsection\label{spendstatement}\label{sproutnullifierintegrity}\label{sproutspendauthority}%

Each proof has public inputs, which appear in the transaction, and a witness, which stays with the prover, and a node verifying the proof learns nothing beyond the checks below passing.

A spend proof shows the spent note's commitment is in the tree under the anchor, the nullifier is the right one for the note, and the randomized key $\mathit{rk}$ disguises the owner's key. The proof also shows the value commitment hides the note's value and the address of the note comes from the same keys, and only the tree check is waived for a note of zero value. An output proof shows the new note's commitment and value commitment are made correctly.

An Orchard Action proves both sides at once, sets the new note's $\rho$ to the spent note's nullifier, and lets a side whose flag is off carry only a dummy note. From NU6.3, when cross-address payments are disabled, the proof also requires the new note to go to the same address as the spent note. The Sprout proof checks the same kinds of facts for two notes in and two out, together with the balance and the tie between the spent notes and the transaction's signing key.

\lsubsection{Encrypting and finding notes}{readableencryption}
\phantomsection\label{decryptivk}\label{decryptovk}\label{saplingandorchardencrypt}\label{saplingandorchardinband}\label{saplinginband}\label{sproutinband}%

The recipient took no part in making the transaction, so the note has to reach the recipient through the block chain. In Sapling and Orchard the sender makes a fresh ephemeral key for every note, combines the ephemeral key with the transmission key of the address to reach a shared secret, and encrypts the note under a key made from the secret. Sprout shares one ephemeral key between the two new notes of a JoinSplit. A second, shorter ciphertext lets the sender's outgoing viewing key read the payment later, and a sender who chose no outgoing viewing key fills the second ciphertext with an encryption under a random key nobody holds.

\textbf{Trial decryption.} The recipient's wallet tries every output on the chain with the incoming viewing key, like trying one key in every locked mailbox, and keeps a note only when the note rebuilt from the decrypted values matches the note commitment on the chain. The rebuilt note shows what arrived but not who sent the note, because the proof does not check the ciphertext and a note carries no sender address. Since Canopy the recipient also uses $\mathit{rseed}$ to check the sender built the note and the ephemeral key correctly \cite{ZIP-212}.

Wallets must use the ephemeral key bytes exactly as the bytes appear on the chain. A wallet may also read transactions still waiting in the mempool, but must treat what the wallet learns as provisional and private, and must not assume the transaction will be mined.

\textbf{Scanning.} To tell whether a received note has been spent, the wallet computes the note's nullifier and watches for the nullifier in later spends. Sapling and Orchard wallets can scan with a full viewing key alone, while Sprout needs the spending key.

\lsection{Concrete Protocol}{concreteprotocol}

\lsubsection{Numbers and bytes}{readablenumbers}

Zcash stores every whole number at a fixed size and with the lowest byte first, unless a rule says otherwise. A few encodings put the highest byte first instead, and each such encoding says so.

\lsubsection{Proving systems}{readableprovingsystems}
\phantomsection\label{bctv}%

A proof computes in the field of one elliptic curve, so the choice of proving system shapes a whole shielded protocol. The curves, hashes and commitments around the proof are chosen to be efficient inside the proof.

\textbf{BCTV14.} Sprout launched with BCTV14 proofs over the BN-254 pairing, made by a fork of the libsnark library. A proof takes 296 bytes.

BCTV14 has a flaw which could have let someone prove a false statement, and so create value, before the Sapling upgrade, although no evidence shows anyone did. The flaw does not affect the zero-knowledge property. Zcash now uses BCTV14 only to check proofs made before the Sapling upgrade. New forks of Zcash must not use BCTV14, and other users of the protocol should stop using BCTV14 as soon as possible. A node which starts from a checkpoint on a block after the Sapling upgrade may skip verifying BCTV14 proofs.

\textbf{Groth16.} From the Sapling upgrade, in transactions of version 4 and later, JoinSplits, Spends and Outputs all carry Groth16 proofs over the BLS12-381 pairing, made by the bellman library. A proof takes 192 bytes.

\textbf{Halo 2.} Orchard and Ironwood Actions, in transactions of version 5 and version 6, carry Halo 2 proofs \cite{Zcash-halo2}.

\textbf{Checking proof elements.} A BCTV14 or Groth16 proof is a list of encoded curve points. A proof whose elements are not well formed is not valid, even if the proof equations hold. For each element, the verifier must check the leading byte or bits have the required form, the remaining bits are a number below the size of the field, and the result is a point of the right order. Every Groth16 element needs the order check, and among the BCTV14 elements only the one in the second group of the pairing does. The point at infinity never appears in a proof and has no encoding.

\textbf{Parameters.} BCTV14 and Groth16 each need a proving key and a verifying key for every circuit, and Zcash's keys came from multi-party computations \cite{BGG2017} \cite{BGM2017}. Software must use exactly the keys made for the Zcash block chain, with a proving system compatible with the library which made the proofs.

\lsubsection{Elliptic curves}{readablecurves}
\phantomsection\label{jubjub}%

Keys and commitments are checked inside the proof, and both are built from curve points. A curve is efficient inside a proof when the curve's coordinates lie in the field the proof computes in, so Sapling and Orchard each add a curve built over the field of the proving system.

\textbf{Jubjub.} Sapling's curve is Jubjub, defined over the field in which BLS12-381 proofs compute. Jubjub is a twisted Edwards curve whose addition law has no exceptional cases. The number of points is 8 times a large prime $r$, and the protocol works in the subgroup of order $r$. A point is encoded as the $v$-coordinate with one extra bit for the sign of the $u$-coordinate.

\textbf{Pallas and Vesta.} Orchard's curves form a cycle, where the coordinate field of each curve is the field of point multipliers of the other. Vesta serves the proving system, and Pallas carries the keys and commitments. Both curves have a prime number of points, so every point except the identity point has the full order and no subgroup check is needed. A point is encoded as the $x$-coordinate with one extra bit for the sign of the $y$-coordinate, and the identity point is encoded as all zero bytes.

\textbf{Decoding a point.} An encoding arrives from an untrusted party, so decoding can fail. A decoder for Jubjub, Pallas or Vesta must reject a coordinate not below the size of the field. The decoder recovers the second coordinate with a square root, and must not assume the square root exists or the bytes describe a point on the curve. The same rule on square roots applies to BN-254 and BLS12-381 points.

Each point of Pallas and Vesta has exactly one valid encoding. The Jubjub decoder also accepts two encodings no encoder produces, one for the identity point $(0, 1)$ and one for the point $(0, -1)$, each with the sign bit set. Such an encoding is called non-canonical, and a rule which requires a canonical encoding rejects both.

\textbf{One coordinate for a point.} A note commitment goes into the tree as one coordinate rather than a whole point. Sapling keeps the $u$-coordinate of the Jubjub point, and two different points of the prime-order subgroup never share a $u$-coordinate. Orchard keeps the $x$-coordinate of the Pallas point, which a point shares only with its negative. The identity point gets the value 0, which no other point has.

\textbf{Hashing onto a curve.} Commitments and addresses need fixed curve points for which nobody knows a relation, meaning nobody can write one point as a known multiple of another. A group hash makes such points by hashing an input and mapping the result onto the curve. A label fixed for each use, called a personalization, goes into the hash and keeps the points of different uses apart.

For Jubjub, the group hash runs BLAKE2s over a public random string fixed in advance followed by the input, decodes the output as a point, and multiplies the point by 8 to land in the prime-order subgroup. The hash fails if the output does not decode or the product is the identity point, and the fixed points come from retrying with a counter byte from 0 upward until the hash succeeds. The random string was derived from a Bitcoin block hash \cite{Bowe2018} and also seeded the multi-party computation for the Sapling parameters.

For Pallas and Vesta, the group hash follows the standard hash-to-curve method with the simplified SWU map \cite{ID-hashtocurve}. BLAKE2b turns the input into two field elements, each element is mapped to a point on a related curve, and the sum of the two points is carried over to Pallas or Vesta. The method needs no random string, and where Zcash's definition and the standard differ, Zcash's definition holds.

\lsubsection{Hash functions}{readablehashes}
\phantomsection\label{concretecrhivk}\label{sinsemillasecurity}%

Sprout computes SHA-256 inside the proof. Sapling and Orchard instead build the note commitment tree and note commitments from hashes designed to be efficient inside a proof, and keep general-purpose hashes for most other work.

\textbf{SHA-256 and BLAKE2.} Sprout uses SHA-256 for note commitments and the bare SHA-256 compression function, which hashes one block without padding, for the Merkle tree and the pseudo-random functions. Double SHA-256 hashes block headers, and SHA-512 appears only inside Ed25519. BLAKE2b hashes the transaction for signing since Overwinter, derives keys, serves inside RedDSA and drives the Equihash puzzle. BLAKE2s gives the Sapling nullifier and the Sapling incoming viewing key, both computed inside the Spend proof, and the group hash onto Jubjub. Nearly every use of BLAKE2 has a personalization of its own.

\textbf{Pedersen hashes.} Sapling needs a hash made of Jubjub arithmetic for the note commitment tree and for note commitments. A Pedersen hash cuts the message into 3-bit chunks, gathers up to 63 chunks into a segment, reads each segment as a number, and adds up one fixed curve point per segment multiplied by the segment's number. Two messages of equal length with the same hash would give a relation between the fixed points, so finding a collision is as hard as the discrete logarithm problem on Jubjub. The guarantee holds only between messages of one fixed length for a given personalization, and a Pedersen hash promises nothing else expected of a general hash function.

\textbf{Sinsemilla.} Halo 2 can look values up in a table efficiently, and Orchard uses a hash designed around the lookup. Sinsemilla starts a running total at a fixed point chosen by the personalization. For each 10-bit piece of the message, Sinsemilla looks up one of 1,024 fixed points, adds the point to the running total, and then adds the earlier total once more. Collisions are again as hard as the discrete logarithm problem, under the same limit to messages of one fixed length.

Sinsemilla uses a cheaper addition formula which fails in rare cases, for example when the two points share an $x$-coordinate. A message which makes the hash fail would give a relation between the fixed points, so finding one must be infeasible.

\textbf{Poseidon.} The Orchard nullifier needs a pseudo-random function made of field arithmetic. Poseidon is a permutation over three elements of the Pallas coordinate field, used as a sponge which absorbs two elements and returns one. The nullifier also rests on the discrete logarithm problem, so a weakness in Poseidon alone, or a break of the discrete logarithm alone, would not be enough to break the nullifier.

\textbf{Merkle trees.} Each tree hashes two child values into one parent value, down a depth of 29 in Sprout and 32 in Sapling and Orchard. Sprout applies the SHA-256 compression function to the two children. Sapling applies a Pedersen hash, and Orchard applies Sinsemilla, to a prefix giving the layer followed by the two children, so a value from one layer cannot stand in for a value from another. If Sinsemilla fails, the Orchard tree hash returns 0. An empty leaf holds a fixed value which no Sapling or Orchard note commitment can equal, 1 in Sapling and 2 in Orchard, and all zero bits in Sprout.

\lsubsection{Commitments}{readablecommitments}

A proof recomputes the note commitment, so Sapling and Orchard build note commitments from the same hash as the tree, and Sprout from SHA-256.

\textbf{Note commitments.} A Sprout note commitment is the SHA-256 hash of the paying key, the value, $\rho$ and the trapdoor. A Sapling note commitment is the Pedersen hash point of the note's value, diversified base and transmission key, plus one more fixed point multiplied by the trapdoor. An Orchard note commitment is built the same way from Sinsemilla, over the diversified base, the transmission key, the value, $\rho$ and one further random value of the note.

The added point makes the Sapling and Orchard commitments hide the note against any attacker, however powerful. Changing the note behind a commitment is as hard as finding a hash collision. Orchard also derives the incoming viewing key as a Sinsemilla commitment to $\mathit{ak}$ and $\mathit{nk}$.

\textbf{Value commitments.} The hashes behind note commitments scramble their input, so two note commitments cannot be added to give a commitment to the sum of the values. Value commitments therefore keep the plain two-point form, on Jubjub for Sapling and on Pallas for Orchard, with both fixed points made by the group hash. A Sapling value commitment could by rare chance be the identity point, which the rules for Spends and Outputs reject, and a wallet may pick a new trapdoor until the commitment is not the identity point.

\lsubsection{Pseudo-random functions and permutations}{readableprfs}
\phantomsection\label{concreteprfs}%

The proof recomputes a note's nullifier, so each protocol builds the nullifier function from a hash the proof can compute. Functions used only by wallets are built from BLAKE2b.

\textbf{Sprout.} All four Sprout functions use the SHA-256 compression function, and the first four bits of the input differ between them, so no two functions ever hash the same input. The functions give the keys of an address, the nullifier, the value tying each spent note to $h_{\mathsf{Sig}}$, and the $\rho$ of each new note. The value $h_{\mathsf{Sig}}$ is a BLAKE2b hash of a random seed, the nullifiers of the JoinSplit and the public key of the transaction's JoinSplit signature.

\textbf{Sapling.} The nullifier is the BLAKE2s hash of $\mathit{nk}$ and $\rho$, and the $\rho$ of a note is the note commitment point plus a fixed point multiplied by the note's position in the tree. BLAKE2b keyed by the spending key expands the spending key into further secrets. BLAKE2b keyed by the outgoing viewing key gives the key of the second, shorter ciphertext of an Output.

\textbf{Orchard.} Orchard keeps the BLAKE2b function for the key of the second ciphertext, and uses Poseidon keyed by $\mathit{nk}$ as part of deriving the nullifier from $\rho$.

\textbf{Diversifiers.} A wallet needs many diversifiers with no two alike. Orchard makes diversifiers with a pseudo-random permutation, encrypting the diversifier index under the diversifier key with the FF1 mode of AES-256 \cite{NIST2016}, and \cite{ZIP-32} does the same for Sapling. A permutation never maps two indices to one diversifier, and diversifiers picked at random would begin to collide after about $2^{44}$ choices.

\textbf{Diversified addresses.} Every diversified address needs a curve point of its own, the diversified base, made by applying the group hash to the diversifier. In Sapling the hash can fail, and a diversifier for which the hash fails gives no address. In Orchard the hash always gives a point, and if the point were the identity point the wallet would use the hash of the empty input instead. A wallet should not let another party choose the diversifier of a new address, because whoever chooses the diversifier can link the other addresses of the same incoming viewing key.

\lsubsection{Encryption}{readablecipher}

The shared secret between sender and recipient comes from the transmission key in the address, so key agreement runs on the curve the address is built on.

\textbf{Key agreement.} Sprout transmission keys are Curve25519 keys \cite{Bernstein2006}, and a Curve25519 private key must have the fixed bit pattern called clamping. Sapling uses Diffie--Hellman on Jubjub and multiplies the shared point by 8, so the shared secret always lies in the prime-order subgroup. Orchard uses plain Diffie--Hellman on Pallas, where every point already has prime order.

\textbf{Key derivation.} The key is a BLAKE2b hash of the shared secret together with the ephemeral key exactly as encoded in the transaction. Sprout also hashes in $h_{\mathsf{Sig}}$, the recipient's transmission key and the position of the note in the JoinSplit.

\textbf{Sealing the note.} The cipher is ChaCha20-Poly1305 in the form of \cite{RFC-7539}, with a 256-bit key and no associated data. Each key encrypts only one message, so the nonce is always zero.

\textbf{The encrypted note.} A Sapling or Orchard note plaintext holds the version byte, the diversifier, the value, the commitment trapdoor or $\mathit{rseed}$, and the memo. A Sprout note plaintext holds $\rho$ in place of the diversifier.

\lsubsection{Signatures}{readablesignatures}

Nodes check signatures directly rather than inside a proof, and every node must accept exactly the same signatures.

\textbf{Ed25519.} The throwaway key of a Sprout transaction is an Ed25519 key \cite{BDLSY2012}, with SHA-512 as the hash. A signature is a point $R$ and a number $S$, checked against a public key $A$. $S$ must be less than the order of the base point, and $R$ and $A$ must decode to points on the curve. Decoding is more lenient than the Ed25519 standard \cite{RFC-8032}: an encoded coordinate may be larger than the field allows, and three encodings the standard rejects are accepted.

Before Canopy, $R$ must also not be one of 11 listed encodings. The check is the equation $S \cdot B = R + c \cdot A$, where $B$ is the base point and $c$ is the SHA-512 hash of $R$, $A$ and the message. The list was meant to exclude points of small order but does not cover all of them, and the list does not apply to $A$.

From Canopy the list is dropped and both sides of the equation are multiplied by 8, and nodes may check signatures in batches. Every signature valid under the earlier rules is valid under the later rules, so a node which starts from a checkpoint on the Canopy activation block may apply the later rules to the whole chain.

\textbf{RedDSA.} Spend authorization signatures and binding signatures use RedDSA, a Schnorr signature, as RedJubjub on Jubjub for Sapling and as RedPallas on Pallas for Orchard. A signature is a point $R$ and a number $S$. The verifier hashes $R$, the public key $\mathit{vk}$ and the message with BLAKE2b into a number $c$ and checks $S \cdot G = R + c \cdot \mathit{vk}$ for the base point $G$. Both sides are multiplied by the cofactor of the curve, 8 on Jubjub and 1 on Pallas.

A signature is valid only if $R$ decodes to a point, $S$ is less than the order of the prime-order subgroup, and the equation holds. From NU5 the encoding of $R$ must also be canonical, a rule which holds for every earlier block on Mainnet and Testnet as well. The bytes of $R$ go into the hash exactly as the bytes appear in the signature, and the verifier does not check the order of $R$. Nodes may check RedDSA signatures in batches. Other protocols which adopt RedDSA should always require a canonical $R$.

\textbf{Base points.} Re-randomizing a key adds a random number to the private key and the same number multiplied by $G$ to the public key. A spend authorization signature has a base point of its own. A binding signature takes as base point the fixed point which carries the trapdoor in a value commitment, so a valid binding signature proves knowledge of the summed trapdoors. Binding signatures do not re-randomize keys.

\lsubsection{Addresses and keys}{readableaddresses}

A user handles addresses and keys as text, so each has a raw encoding as bytes and a text encoding with a checksum. The leading characters show the kind of address or key and the network.

\textbf{Transparent addresses.} A transparent address is the hash of a script, for a pay-to-script-hash address, or of a public key, for a pay-to-public-key-hash address. The text encoding is Base58Check as in Bitcoin, and on Mainnet the first kind starts with \texttt{t3} and the second with \texttt{t1}. Transparent private keys are encoded as in Bitcoin.

\textbf{Sprout.} Sprout uses Base58Check as well. An address holds the paying key and the transmission key and starts with \texttt{zc} on Mainnet. An incoming viewing key starts with \texttt{ZiVK} on Mainnet and is not valid unless the receiving key inside is clamped. A spending key starts with \texttt{SK} on Mainnet.

\textbf{Sapling.} Sapling uses Bech32 as \cite{ZIP-173} defines, without the usual limit on length. An address is the diversifier followed by the transmission key $\mathit{pk_d}$, and starts with \texttt{zs} on Mainnet. The address is not valid if $\mathit{pk_d}$ fails to decode, has a non-canonical encoding, or is not a point of order $r$, which rules out the identity point.

A Sapling incoming viewing key must lie between 1 and $2^{251} - 1$, and starts with \texttt{zivks} on Mainnet. The encoding is deprecated, because the diversifier key is missing, and a unified incoming viewing key is preferred. A full viewing key holds $\mathit{ak}$, $\mathit{nk}$ and the outgoing viewing key, and starts with \texttt{zviews} on Mainnet. The key is not valid if either point fails to decode, $\mathit{ak}$ is not a point of order $r$, or $\mathit{nk}$ is outside the prime-order subgroup. A spending key starts with \texttt{secret-spending-key-main}.

\textbf{Unified addresses.} A user with several kinds of address needs one address to hand out. A unified address \cite{ZIP-316} holds at most one receiver of each kind, and a payer must use the most preferred kind the payer's software supports, in the order Orchard, Sapling, transparent. A unified address must hold at least one shielded receiver and cannot hold both a pay-to-script-hash and a pay-to-public-key-hash receiver. No Sprout receiver exists, since Sprout can no longer receive funds.

Unified addresses use Bech32m \cite{BIP-350} without a length limit, since the Bech32m checksum copes better with encodings of varying length. Before encoding, the contents are jumbled, which guards against an attacker replacing the address with another when the user checks only part of the text. Unified addresses are recommended for all new applications, unless the address must work with software which accepts only the earlier formats. Unified incoming viewing keys and unified full viewing keys hold sets of viewing keys in the same way.

\textbf{Orchard.} Orchard addresses and viewing keys have raw encodings only and appear as text only inside the unified formats. A raw address is the diversifier and the encoding of $\mathit{pk_d}$, and is not valid if $\mathit{pk_d}$ fails to decode or is the identity point. A raw incoming viewing key is the diversifier key and a number, which must lie between 1 and $q - 1$ for $q$ the size of the Pallas coordinate field.

A raw full viewing key is three field elements, $\mathit{ak}$, $\mathit{nk}$ and the randomness $\mathit{rivk}$. The key is not valid if any element is not canonically encoded, or if $\mathit{ak}$ is not the $x$-coordinate of a Pallas point other than the identity point. The key is also not valid if either incoming viewing key derived from the key is zero or fails to derive. An Orchard spending key is encoded with Bech32m and starts with \texttt{secret-orchard-sk-main} on Mainnet.

\lsection{Network Upgrades}{networkupgrades}

A network upgrade is a planned change to the consensus rules which every node adopts at an agreed activation height \cite{ZIP-200}.

Zcash launched with the Sprout protocol on 28 October 2016 and has upgraded eleven times since.

\textbf{Overwinter} (June 2018) made every transaction name the upgrade the transaction was built for, so no transaction can be replayed across an upgrade, and let a transaction expire at a chosen height.

\textbf{Sapling} (October 2018) added the Sapling pool, with shielded payments orders of magnitude faster than in Sprout, full viewing keys and diversified addresses.

\textbf{Blossom} (December 2019) halved the time between blocks from 150 to 75 seconds.

\textbf{Heartwood} (July 2020) let miners take the block reward straight into a Sapling address and made each block header commit to the history of the chain for light clients.

\textbf{Canopy} (November 2020) arrived with the first halving, replaced the Founders' Reward with a development fund of 20\% of the block subsidy, and closed the Sprout pool to new value.

\textbf{NU5} (May 2022) added the Orchard pool, whose Halo 2 proofs need no trusted setup, together with unified addresses.

\textbf{NU6} (November 2024) arrived with the second halving and split development funding between Zcash Community Grants and a lockbox held by the protocol.

\textbf{NU6.1} (November 2025) paid out the lockbox for development grants and extended development funding until the third halving.

\textbf{NU6.2} (June 2026) enabled the Orchard pool again with a corrected circuit, after a soundness vulnerability which could have allowed theft of funds had forced the pool to be disabled.

\textbf{NU6.3} (July 2026) added the Ironwood pool, whose notes support quantum recovery, and closed the Orchard pool so value can only leave the pool.

\textbf{NU7} (November 2026) cut the time between blocks to 25 seconds and deprecated Sprout.

\lsection{Consensus Changes from \BitcoinText}{consensusfrombitcoin}
\phantomsection\label{txnencoding}\label{txnidentifiers}\label{blockheader}\label{equihash}%
\label{workdef}\label{subsidies}\label{foundersreward}\label{fundingstreams}

\Zcash began as a fork of \BitcoinCore version 0.11.2, so a \Zcash node validates blocks and
transactions much as a \Bitcoin node does. The rules below describe only where \Zcash departs
from \Bitcoin.

\begin{enumerate}
  \item \textbf{Transactions.} A transaction keeps \Bitcoin's transparent inputs and outputs and
        adds fields for the shielded protocols, with newer transactions using version 5, carrying
        Sapling and Orchard parts, or version 6, which adds Ironwood. Each transaction names the
        network upgrade it was built for and may name an expiry height after which no block may
        include the transaction, and version 5 and 6 transactions are identified by a hash defined
        in \cite{ZIP-244} and \cite{ZIP-229} rather than by \Bitcoin's hash of the raw bytes.

  \item \textbf{Valid transactions.} A transaction must take value from somewhere and send value
        somewhere, keep each value balance within the total supply of 21 million ZEC, give every
        shielded part a correct encoding and a proof which verifies, refer every shielded spend to an
        earlier tree of note commitments, and carry the signatures binding the shielded parts together, which
        also prove the hidden values balance.

  \item \textbf{The coinbase transaction.} The first transaction in every block collects the block
        subsidy and the fees not removed from circulation, must since NU6 pay out exactly that
        total, begins its script with the block
        height, cannot spend shielded notes, and must make any shielded outputs readable with an
        all-zero outgoing viewing key, while transparent coinbase outputs can be spent only after
        100 further blocks and only by a transaction with no transparent outputs.

  \item \textbf{Blocks.} The block header follows \Bitcoin's, with the nonce widened to 32 bytes,
        an \Equihash solution added, and a field committing to the block's transactions and the
        history of the chain. A block holds at most 2,000,000 bytes, double \Bitcoin's limit, and
        the block's time must fall after the median time of the previous 11 blocks and no more than
        90 minutes beyond that median.

  \item \textbf{Proof of work.} \Zcash replaces \Bitcoin's proof of work with \Equihash, a
        memory-hard puzzle chosen as an attempt to resist mining centralization, and the target
        adjusts after every block rather than every two weeks, following an average over the
        most recent blocks to hold a steady time between blocks. A node follows the valid chain
        carrying the most total work.

  \item \textbf{Issuance.} New ZEC is issued with each block, at most 12.5 ZEC per block after a
        slow start over the first 20,000 blocks, halving roughly every four years so the supply
        never exceeds 21 million ZEC. In the first four years a fifth of each subsidy went to the
        Founders' Reward, and today part of each subsidy goes to development funding, paid either
        to named recipients or into a lockbox held in reserve.

  \item \textbf{What NU7 changes.} NU7, activated in November 2026, brings blocks every 25 seconds, averages
        difficulty over the last 102 blocks, stretches the number of blocks between halvings so
        halvings keep their schedule in time, limits how many shielded spends and outputs a block
        may carry, and through the Network Sustainability Mechanism removes 60\% of transaction
        fees from circulation, to be reissued later as part of the block subsidy.

  \item \textbf{Scripts and BIPs.} \Zcash keeps \Bitcoin's script system with one opcode,
        \texttt{OP\_CODESEPARATOR}, disabled, and applies only the Bitcoin Improvement Proposals
        named in the specification, such as BIP 16 for pay-to-script-hash and BIP 65 for
        \texttt{CHECKLOCKTIMEVERIFY}, while BIP 68 does not apply.
\end{enumerate}

\lsection{From \ZerocashText{} to Zcash}{differences}
\phantomsection\label{trstructure}\label{memodiffs}\label{mintsandpours}\label{faeriegold}\label{internalh}\label{truncation}\label{inbandrationale}\label{crprf}\label{miscdiffs}%

Zcash was built from the Zerocash paper \cite{BCGGMTV2014} and makes two changes to the paper's design.

Every shielded transfer in Zcash carries a zero-knowledge proof, so a note commitment is a single hash. The nested commitment of the paper had a truncated inner hash, which would have let an attacker spend a note twice and create currency out of nothing \cite{HW2016}.

Zcash also derives the $\rho$ of each new note from values the sender cannot repeat, so no two notes on a valid block chain share a $\rho$ or a nullifier. A dishonest sender cannot pay with two notes of which only one can ever be spent, an attack called Faerie Gold, and a wallet restored from the spending key alone needs no record of past $\rho$ values.
