# 4 Abstract Protocol

## 4.1 Cryptographic tools

The protocol is described using abstract cryptographic tools, such as pseudo random functions, commitment schemes and signature schemes, each defined by an interface for the rest of the system and a set of security properties, which chapter 5 fills in with concrete instances. Zcash extends some of the usual definitions, for example by asking some PRFs to also be collision-resistant and some signature schemes to support extra operations. Some requirements are also intentionally stronger than is known to be needed, because the stronger property is simpler or less error-prone to work with, or has been studied more in the literature.

The specification does not claim that instances meeting these abstractions are sufficient, or always necessary, for the security of the whole protocol. The claim is only that a good way to understand each use of a primitive is to model the primitive as an instance of its abstraction, so an instance that fails its abstraction is an error to correct, whether or not the failure leads to a vulnerability. Each property is a claim that may itself be wrong, as with the Zerocash note commitment, which was not binding at the intended security level (§8.5). An abstraction can also be leaky, when an instance imposes conditions its interface does not state, or incomplete, as with side-channel resistance, which the specification mostly does not cover.

*Hash functions* (§4.1.1) are fixed functions with no key, and most of them must be collision-resistant, which means nobody can feasibly find two inputs with the same output. The three Merkle-tree hashes *MerkleCRH^Sprout*, *MerkleCRH^Sapling* and *MerkleCRH^Orchard*, instantiated by SHA256Compress, PedersenHash and SinsemillaHash, combine two child nodes into a parent node of the note commitment tree (§4.9). *MerkleCRH^Sprout* ignores its layer argument and is collision-resistant on the other arguments only, while the Sapling and Orchard hashes are collision-resistant on all arguments, including the layer.

*hSigCRH* (BLAKE2b-256) is collision-resistant and computes the value *h_Sig* of a JoinSplit description, and *EquihashGen* (BLAKE2b) makes the input to the Equihash solver. *CRH^ivk* (BLAKE2s-256, truncated) is collision-resistant and derives the Sapling incoming viewing key *ivk* from *ak* and *nk*, and the Spend statement uses *CRH^ivk* again to check that the spender used the correct keys for the note. *MixingPedersenHash* derives the unique *ρ* of a Sapling note, and the Spend statement uses the same hash to check the *ρ* that goes into the nullifier. *DiversifyHash^Sapling* and *DiversifyHash^Orchard*, built on *GroupHash*, turn a diversifier *d* into the diversified base *g_d* of an address, and *DiversifyHash^Sapling* can fail, returning ⊥ for some diversifiers. Both must be unlinkable: given addresses from two different spend authorities and a third address from one of the two, with three different diversifiers, nobody can tell which authority made the third address.

A *pseudo random function* *PRF_x* (§4.1.2) is a keyed function whose outputs look random to anyone who does not know the key *x*. Sprout uses four independent PRFs, all built from SHA256Compress, in the JoinSplit statement: *PRF^addr* derives the address key *a_pk* from the spending key *a_sk*, *PRF^pk* and *PRF^ρ* bind inputs and outputs to *h_Sig*, and *PRF^nfSprout* makes nullifiers. Sapling and Orchard share *PRF^expand* (BLAKE2b-512), which expands a seed into key material, with the first byte of its input separating its uses in key components, in sending and receiving notes, and in ZIP 32, ZIP 316 and ZIP 2005. *PRF^ockSapling* and *PRF^ockOrchard* (BLAKE2b-256) derive the outgoing cipher key *ock* for note encryption, *PRF^nfSapling* (BLAKE2s-256) makes the Sapling nullifier in the Spend statement, and *PRF^nfOrchard* (PoseidonHash) makes the Orchard nullifier in the Action statement.

Beyond pseudo-randomness, *PRF^addr*, *PRF^ρ* and all three nullifier PRFs must be collision-resistant across keys, which means nobody can feasibly find two different (key, input) pairs with the same output. A caveat on the reuse of the *PRF^expand* key appears with the Orchard key components (§4.2.3).

A *pseudo random permutation* *PRP^d* (§4.1.3) is a keyed, invertible map whose behaviour looks like a random permutation to anyone without the key. *PRP^d* is FF1-AES256 with an empty tweak, and the protocol uses *PRP^d* to make Orchard diversifiers from a diversifier key *dk* and an index; ZIP 32 uses the same construction for Sapling diversifiers.

*Symmetric encryption* *Sym* (§4.1.4) is AEAD_CHACHA20_POLY1305 with a zero nonce. *Sym.Decrypt* gives back the plaintext of an honest ciphertext and returns ⊥ for an invalid one. *Sym* must be one-time (INT-CTXT ∧ IND-CPA)-secure, which means an attacker can neither read the plaintext nor make a new ciphertext that decrypts. "One-time" means an honest party almost surely encrypts only one message under a given key, while the attacker may still make many adaptive chosen-ciphertext queries against that key.

*Key agreement* *KA* (§4.1.5) lets two parties reach a shared secret, each using their own private key and the other party's public key. *KA.DerivePublic* makes a public key from a private key and a base point, *KA.Agree* computes the shared secret, and *KA.FormatPrivate*, where present, turns a bit string into a private key and must keep enough entropy for the key to be secure. The instances are Curve25519 for *KA^Sprout*, Diffie–Hellman with cofactor multiplication on Jubjub for *KA^Sapling*, and Diffie–Hellman on Pallas for *KA^Orchard*.

A *key derivation function* *KDF* (§4.1.6) turns the shared secret from *KA* into a key for *Sym*. *KDF^Sprout* also takes the output index, *h_Sig*, the ephemeral public key *epk* and the recipient's *pk_enc*, while *KDF^Sapling* and *KDF^Orchard* (BLAKE2b-256) take only the shared secret and *epk*. *KA* and *KDF* together must satisfy an adaptive security assumption, and the encryption scheme built from *KA*, *KDF* and *Sym* for each pool must be IND-CCA2-secure, so a ciphertext reveals nothing about the note, and key-private, so a ciphertext does not reveal the recipient's public key (§4.19, §4.20).

A *signature scheme* *Sig* (§4.1.7) has a randomized *Sig.GenPrivate* for signing keys, an injective *Sig.DerivePublic* from a signing key to a validating key, a randomized *Sig.Sign*, and *Sig.Validate*, which accepts every honest signature. Zcash uses four schemes: ECDSA on secp256k1 for transparent script operations such as OP_CHECKSIG, as in Bitcoin; *JoinSplitSig* (Ed25519) for transactions with JoinSplit descriptions; *SpendAuthSig* (RedDSA, as RedJubjub in Sapling and RedPallas in Orchard) for spend authorizations; and *BindingSig* (also RedJubjub or RedPallas) for binding signatures, which enforce the balance of the shielded transfers and prevent their replay in other transactions. The specification says that signatures are "validated" and that proofs are "verified".

*JoinSplitSig* and *BindingSig* must be strongly unforgeable under non-adaptive chosen-message attack (SU-CMA): an attacker who sees signatures on messages of the attacker's choice cannot make any new valid (message, signature) pair, not even a second signature on a message already signed, so the signatures are nonmalleable in the sense of BIP 62. Non-adaptive security is enough because each transaction gets a fresh *JoinSplitSig* key pair used for one signature (§4.11), although Ed25519 is in fact adaptively secure, and the *BindingSig* key comes from the randomness of the value commitments, which gives the same distribution as a fresh key pair for each transaction. Key generation and key derivation are separate algorithms so that the Sapling and Orchard key derivations (§4.2.2, §4.2.3) work, and so the two special signature kinds below have simpler definitions.

A *signature scheme with re-randomizable keys* (§4.1.7.1), used for *SpendAuthSig*, adds a random randomizer *α* with an identity value 𝒪, and two operations, *Sig.RandomizePrivate* and *Sig.RandomizePublic*, which shift a signing key and its validating key by the same *α*. Randomizing the signing key and then deriving the validating key gives the same result as deriving first and then randomizing; a randomized signing key has the same distribution as a fresh signing key; *Sig.RandomizePrivate* with a fixed *α* is injective and easily inverted; and the identity randomizer leaves the key unchanged. A randomized validating key and signatures under the key therefore do not reveal the original key, while whoever knows the randomized key and *α* knows the original key.

*SpendAuthSig* must be strongly unforgeable with re-randomized keys under adaptive chosen-message attack (SURK-CMA): the attacker gets the validating key and an oracle that signs any message under any randomization of the signing key, and must not be able to produce a new (message, signature) pair that validates under any randomization of the validating key. Adaptive security over many messages is required, unlike for *JoinSplitSig*, because one key pair can be re-randomized for many notes, and several transactions spending the same note can be revealed to an attacker.

A *signature scheme with key monomorphism* (§4.1.7.2), used for *BindingSig*, puts an abelian group structure on signing keys and on validating keys, with *Sig.DerivePublic* an injective homomorphism, which means the validating key of a sum of signing keys is the sum of the validating keys; the notation also covers differences, and an empty sum is the identity 𝒪. Adding an unknown, independently generated signing key to any signing key must give a result that looks like a fresh signing key, so any sum of signing keys with at least one unknown term looks fresh.

A *commitment scheme* *COMM* (§4.1.8) takes a random trapdoor and an input and makes a commitment that hides the input and binds the committer to the input. Hiding means commitments to any two inputs have computationally indistinguishable distributions, and binding means nobody can feasibly find two different inputs, with any trapdoors, that give the same commitment. Two commitments to the same input under different trapdoors are allowed, and for *NoteCommit^Sapling* and *ValueCommit^Sapling* such pairs are easy to find, because trapdoors are equivalent modulo *r_J*. *COMM.GenTrapdoor* need not be uniform over the trapdoor type, and where *COMM.GenTrapdoor* is not uniform, picking a trapdoor uniformly from the type is incorrect.

The commitment schemes are *NoteCommit^Sprout* (SHA-256); *NoteCommit^Sapling* (windowed Pedersen) and *ValueCommit^Sapling* (homomorphic Pedersen) on Jubjub; and *NoteCommit^Orchard* (Sinsemilla), *ValueCommit^Orchard* (homomorphic Pedersen) and *Commit^ivk* (SinsemillaShortCommit) on Pallas. The Sapling commitments always land in the prime-order subgroup, but their type is the whole curve, because the value commitments in Spend and Output descriptions, and *cmu*, are not directly checked to be in the subgroup. *NoteCommit^Orchard* and *Commit^ivk* can return ⊥, with insignificant probability, and *Commit^ivk* can also return 0, which is not a valid *KA^Orchard* private key; the Orchard key derivation (§4.2.3) handles both cases, and the Action circuit needs no special handling of 0.

A *represented group* (§4.1.9) is an elliptic-curve group together with a byte encoding: a prime subgroup order *r_G*, a cofactor *h_G*, an encoding *repr_G* to a fixed-length bit string, and a decoding *abst_G* which undoes *repr_G* and returns ⊥ for strings that are not points. The decoding can accept non-canonical encodings, strings that decode to a point but are not the point's *repr_G*, and *G^(r)⋆* names the set of canonical encodings of subgroup points only. A *coordinate extractor* *Extract* (§4.1.10) maps a subgroup point to a shorter value, such as the *u*-coordinate on Jubjub (*Extract_J(r)*) or the *x*-coordinate on Pallas (*Extract_P*), and unlike *repr_G* need not be efficiently reversible.

A *group hash* *GroupHash* (§4.1.11) maps an input, under a Uniform Random String (URS), to a point of the prime-order subgroup. With a random URS, the Jubjub group hash, where the hash does not return ⊥, must be reasonable to model as a random oracle, while the Pallas and Vesta group hashes follow the IETF hash-to-curve design with no URS and are heuristically modelled as random oracles too. The URS for Jubjub was chosen verifiably at random (§5.9) after the algorithm was fixed, which mitigates the possibility of a backdoored group hash.

The protocol uses *GroupHash* to make independent generators: the Sapling key bases *𝒢^Sapling* and *ℋ^Sapling*, the generators of the Pedersen hash and the Pedersen commitments, and the base of *DiversifyHash^Sapling*. The property these uses need is Discrete Logarithm Independence, which means nobody can find a nontrivial linear relation between group-hash outputs for distinct inputs; a random oracle almost surely has the property if discrete logarithms are hard, and the property implies collision resistance. Unlinkability of *DiversifyHash* is shown only in the random-oracle model, from the Decisional Diffie–Hellman assumption.

A *represented pairing* *PAIR* (§4.1.12) is a bilinear and nondegenerate map ê from two represented subgroups of the same prime order into a target group, where bilinear means ê([a]P, [b]Q) = ê(P, Q)^(a·b) and nondegenerate means no point of order r in the first group pairs to 1 with every point of the second group. The pairings in use are BN-254 and BLS12-381.

A *zero-knowledge proving system* *ZK* (§4.1.13), of the preprocessing zk-SNARK kind, proves that a statement holds for public primary inputs and secret auxiliary inputs without revealing anything about the secret inputs beyond what the statement implies. *ZK.Gen* makes a proving key and a verifying key, *ZK.Prove* makes a proof from satisfying inputs, and *ZK.Verify* checks a proof against the primary input. Three properties must hold with overwhelming probability over the key generation: completeness, meaning an honest proof always verifies; knowledge soundness, meaning an efficient extractor can get satisfying secret inputs from anyone who makes a verifying proof; and statistical zero knowledge, meaning a simulator without the secret inputs makes proofs nobody can tell from real ones. The properties do not include nonmalleability, and the protocol design must take the omission into account.

Zcash uses three proving systems. *ZK^JoinSplit*, for the Sprout JoinSplit statement, uses BCTV14 on BN-254 before Sapling activation and Groth16 on BLS12-381 after activation, with the keys chosen by the activation height of the block that holds the proof (§5.7, §5.8). *ZK^Spend* and *ZK^Output*, for the Sapling Spend and Output statements, use Groth16, and *ZK^Action*, for the Orchard Action statement from NU5, uses Halo 2 on Vesta, which makes its parameters on the fly with no parameter files; *ZK^Action* names its keys explicitly because more than one version of the Orchard circuit has been deployed.

## 4.2 Keys

Each shielded protocol makes its keys from one random spending key, and every derivation step names a fixed tool. A key that fails a check is never repaired: the wallet discards the spending key and starts again with a new random one (§4.2).

The Sprout spending key *a_sk* is a random bit sequence, and every other Sprout key comes from *a_sk* through the pseudo-random function *PRF^addr* (§4.2.1). *PRF^addr* keyed by *a_sk* and applied to the input 0 gives the paying key *a_pk*, and applied to the input 1 gives a bit string which *KA^Sprout* turns into the receiving key *sk_enc* by Curve25519 clamping. The transmission key *pk_enc* is the *KA^Sprout* public key for *sk_enc* on the fixed base point, and the Sprout address is the pair (*a_pk*, *pk_enc*).

The Sapling spending key *sk* is a random bit sequence, and the wallet keys *PRF^expand* with *sk* and applies the function to three different one-byte inputs (§4.2.2). The outputs for inputs 0 and 1 are read as integers and reduced modulo the order of the Jubjub prime-order subgroup, which gives the spend authorizing key *ask* and the nullifier private key *nsk*, and the output for input 2 is truncated to give the outgoing viewing key *ovk*. If *ask* is zero, the wallet discards *sk* and repeats with a new one. (§3.1 calls *nsk* the nullifier private key and the pair (*ak*, *nsk*) the proof authorizing key, but §4.2.2 calls *nsk* alone the proof authorizing key.)

From *ask* and *nsk* the wallet makes the public halves: the spend validating key *ak* is the *SpendAuthSig^Sapling* public key for *ask*, and the nullifier deriving key *nk* is *nsk* times a fixed Jubjub point *ℋ^Sapling*, found by hashing the string "Zcash_H_" into the curve. *CRH^ivk* then takes the encodings of *ak* and *nk* and gives the incoming viewing key *ivk*, a nonzero integer used as a key-agreement private key, and if *ivk* is zero the wallet discards *sk* and repeats. The full viewing key is (*ak*, *nk*, *ovk*).

All diversified addresses of one Sapling spending key share the same full viewing key and the same incoming viewing key. To make an address from *ivk*, the wallet picks a random diversifier *d* and hashes *d* into a curve point with *DiversifyHash^Sapling*, picking a new *d* whenever the hash gives no point (⊥), until the hash gives a valid diversified base *g_d*. The diversified transmission key *pk_d* is the *KA^Sapling* public key which *ivk* makes on the base *g_d*, and the address is the pair (*d*, *pk_d*).

Each Sapling spending key also has a default address, whose diversifier looks random, and which nobody without *sk* can tell apart from an address with a truly random diversifier. The default diversifier comes from *PRF^expand* keyed by *sk* and applied to the input [3, *i*], truncated to diversifier length, for *i* = 0, 1, 2, …, with the first *i* whose diversifier gives a valid *g_d* chosen; if no *i* works (probability about 2^−256), the wallet discards *sk* and repeats. The zcashd wallet does not use this procedure and picks diversifiers as ZIP 32 describes.

The protocol does not prevent "vanity" diversifiers, which make the Bech32-encoded address start with a chosen string. A vanity address gives weaker privacy than a random diversifier, because anyone can see the address is a vanity address, and the address can reveal more than intended about who made the address. Address generators MAY encode information in the diversifier for the recipient to read back, but the RECOMMENDED place for such information is the ZIP 32 diversifier index, which only a holder of the diversifier key *dk* can read. *PRF^expand* gives 512 bits, and the reduction modulo the 252-bit subgroup order adds only a small bias, so *ask* is computationally indistinguishable from a freshly generated signing key, and *nk* is likewise near-uniform over the key space of *PRF^nfSapling*.

The Orchard spending key *sk* is a random bit sequence, and the wallet MUST derive every Orchard key component as follows (§4.2.3). As in Sapling, each step keys *PRF^expand* with *sk* and gives a fixed one-byte input (0x06, 0x07, 0x08, 0x0C), and the output is reduced modulo the Pallas scalar order (*ToScalar^Orchard*), reduced modulo the Pallas base-field order (*ToBase^Orchard*), or truncated. The nullifier deriving key *nk* always comes from *sk* with input 0x07, reduced to a base-field element.

Orchard has two ways to make the spend authorizing key *ask*, the spend validating key *ak* and the commitment randomness *rivk*, and a flag *use_qsk* chooses between them. In the standard way (*use_qsk* false), *ask* comes from *sk* with input 0x06, and if *ask* is zero the wallet discards *sk* and repeats. The wallet computes the *SpendAuthSig^Orchard* public point *ak_P* for *ask*, replaces *ask* by −*ask* if the sign bit ỹ of the encoding of *ak_P* is 1, takes *ak* as the x-coordinate of *ak_P*, and derives *rivk* from *sk* with input 0x08. Keys matching versions of the specification before 2026.8.0 must use *use_qsk* false.

The other way (*use_qsk* true) does not derive *ask* from *sk*, and serves protocols which make shares of *ask* by distributed generation, such as FROST Distributed Key Generation (ZIP 312), and hardware wallets which keep *ask* on the device apart from the authority to make proofs for the Recovery Protocol (ZIP 2005). The wallet obtains *ak_P* by any suitably secure method that makes the last bit of the encoding of *ak_P* equal to 0, such as generating *ask* directly, or FROST key generation, in which t of n participants share the spend-authorization material, and *ak* is again the x-coordinate of *ak_P*. The quantum spending key *qsk* comes from *sk* with input 0x0C, truncated to 32 bytes, the quantum intermediate key *qk* is BLAKE3 key derivation of *qsk* under a fixed ZIP 2005 context string, and *rivk* is *PRF^expand* keyed by *qk* and applied to 0x0D followed by *ak* and *nk*, reduced to a scalar.

From *ak*, *nk* and *rivk*, which form the full viewing key, the wallet makes the remaining keys in the same way for both methods. *Commit^ivk* commits to *ak* and *nk* with randomness *rivk*, which gives the incoming viewing key *ivk*, the x-coordinate of a Pallas point used as the *KA^Orchard* private key, and if *ivk* is zero or the commitment gives no point (⊥), the wallet discards *sk* and repeats. *PRF^expand* keyed by *rivk* and applied to 0x82 followed by *ak* and *nk* gives one output, which the wallet splits into the diversifier key *dk* and the outgoing viewing key *ovk*, and the Orchard incoming viewing key is the pair (*dk*, *ivk*).

Each Orchard key also has an internal set of keys, which comes from the ZIP 32 internal derivation of (*ak*, *nk*, *rivk*), keeps the same *ak* and *nk*, and has a new *rivk_internal*. The wallet computes *ivk_internal*, *dk_internal* and *ovk_internal* from the internal keys with the same steps, and again discards *sk* and repeats if *ivk_internal* is zero or ⊥. If a wallet does not make *ask*, *ak*, *nk*, *rivk* and *rivk_internal* as specified, the notes may not be recoverable under ZIP 2005 if quantum attacks become practical; recovery also needs *sk*, either kept or re-derivable, and knowledge of whether *use_qsk* was used, and with FROST also the group validating key *ak* and the signers' material.

All diversified addresses of one Orchard key share the same full viewing key, incoming viewing key and outgoing viewing key. To make an address from (*dk*, *ivk*), the wallet picks a diversifier index *index* no earlier address used, and the pseudo-random permutation *PRP^d* (FF1-AES256 keyed by *dk*) turns *index* into the diversifier *d*. *DiversifyHash^Orchard* turns *d* into the diversified base *g_d* and, unlike the Sapling hash, always gives a point, because a hash result equal to the identity point is replaced by a fixed fallback point, so the wallet never retries. *pk_d* is the *KA^Orchard* public key which *ivk* makes on *g_d*, the address is (*d*, *pk_d*), and the address with index 0 is the default address.

Diversifier indices SHOULD NOT be chosen at random, and ZIP 32 specifies how hierarchical deterministic wallets use the indices; address generators MAY encode information in the diversifier index, which the recipient can recover with *dk*. *rivk* is used twice, as the randomizer of *Commit^ivk* and as the *PRF^expand* key which makes *dk* and *ovk*, and if an adversary knows *dk* and *ovk*, the double use prevents a proof that *Commit^ivk* is perfectly hiding here; the specification models the double use with a joint assumption on Pallas scalar multiplication and *PRF^expand*, and the authors consider an exploitable interaction with BLAKE2b extremely unlikely. *ivk* can take only about half of the scalar values, and the specification does not expect the non-uniformity to cause a security issue.

## 4.3 Shielded parts of a transaction

A transaction can carry any number of JoinSplits, and a transaction with at least one JoinSplit also carries a validating key and a signature covering all of them. Each JoinSplit spends two old notes and creates two new ones, and records ten things. Two amounts connect the JoinSplit to the transparent side of the transaction: the first is taken from the transparent side and moved into the new shielded notes, and the second is released from the spent notes back to the transparent side. The JoinSplit then names an anchor, the state of the Sprout note commitment tree at an earlier block, or the state just after an earlier JoinSplit in the same transaction, which the spent notes must belong to.

Next come the nullifiers of the two spent notes, the note commitments of the two new notes, a temporary public key and the two encrypted new notes, which together let each recipient find and read the recipient's note, and a random seed chosen afresh for each JoinSplit. The last two parts tie the JoinSplit to its transaction. A hash of the random seed, the two nullifiers and the transaction's validating key gives a value called *h_sig*, and the JoinSplit carries one tag for each spent note, made from *h_sig* and the note's spending key. The zero-knowledge proof covers the amounts, the anchor, the nullifiers, the note commitments, *h_sig* and the tags, so neither the proof nor the tags can be lifted into a different transaction. The proof uses BCTV14 before Sapling and Groth16 from Sapling onward.

Four rules apply. Every part must have the right type, so neither amount may exceed 21 million ZEC; the proof must verify; at most one of the two amounts may be non-zero, so a JoinSplit moves value into the shielded side or out of the shielded side but never both at once; and since Canopy the amount moved into Sprout must be zero, which closes the Sprout pool to new value (§4.3).

A transaction can carry any number of Spends, each of which spends one Sapling note, records six things and is authorized by a spend authorization signature (§4.4). The value commitment *cv* hides the value of the spent note, and the anchor *rt* names the state of the Sapling note commitment tree at an earlier block, which the spent note must belong to. The nullifier *nf* of the spent note follows, then a randomized validating key *rk*, the zero-knowledge proof, which covers *cv*, *rt*, *nf* and *rk* and proves the Spend statement (§4.18.2), and the spend authorization signature *spendAuthSig*.

Every part of a Spend MUST be a valid encoding of its type, neither *cv* nor *rk* may be a point of small order, and the proof MUST verify. *spendAuthSig* MUST be a valid signature, checked with *rk*, over the transaction's SIGHASH hash, computed with SIGHASH_ALL and not tied to any transparent input (§4.10), and from NU5 the check also rejects a non-canonical encoding of the signature's *R* point, a stricter check which also holds for the blocks before NU5 on Mainnet and Testnet. An implementation MAY pick a new value commitment trapdoor until the commitment is not the zero point, and the rule against small-order points also excludes non-canonical encodings of *cv* and *rk*, as ZIP 216 requires.

A transaction can also carry any number of Outputs, each of which creates one Sapling note and records six things, and no signature goes with an Output (§4.5). The value commitment *cv* hides the value of the new note, and *cm_u* is the u-coordinate of the new note's commitment. A temporary public key *epk* and two ciphertexts follow: *C_enc* holds the encrypted note for the recipient, and *C_out* lets the holder of the outgoing cipher key, which a full viewing key can derive, recover the recipient's *pk_d* and the ephemeral private key *esk*, and with them the whole note plaintext (§4.20).

The last part of an Output is the zero-knowledge proof, which covers *cv*, *cm_u* and *epk* and proves the Output statement (§4.18.3). Every part MUST be a valid encoding of its type, neither *cv* nor *epk* may be a point of small order, and the proof MUST verify, and the two notes for Spends apply in the same way, with *epk* in place of *rk*.

From NU5 a transaction can carry Actions, each of which spends one note and creates one note (§4.6). Version 5 and version 6 transactions carry a list of Actions for the Orchard pool, version 6 transactions also carry a second list for the Ironwood pool, and version 4 transactions cannot carry Actions. Each Action records thirteen things and, like a Spend, is authorized by a spend authorization signature.

On the spending side an Action holds the anchor *rt*, the state of the pool's note commitment tree at an earlier block, then the nullifier *nf* of the spent note, a randomized validating key *rk* and the signature *spendAuthSig*. On the output side the Action holds *cm_x*, the x-coordinate of the new note's commitment, a temporary public key *epk*, and the two ciphertexts *C_enc* and *C_out*, which serve as in an Output. One value commitment *cv_net* covers both sides and hides the value of the spent note minus the value of the new note.

Three flags complete the Action: *enableSpends* allows the spent note to have a non-zero value, *enableOutputs* allows the new note to have a non-zero value, and from NU6.3 *enableCrossAddress* allows the new note's expanded receiver, the pair (*g_d*, *pk_d*) of ZIP 2006, to differ from the spent note's expanded receiver. The proof is a Halo 2 proof of the Action statement (§4.18.4) and covers *cv_net*, *rt*, *nf*, *rk*, *cm_x*, *enableSpends*, *enableOutputs* and *disableCrossAddress*, which is 1 minus *enableCrossAddress*. The anchor and the flags are the same for every Action of one pool in a transaction, and the transaction stores them once per pool, with the proofs of all Actions in a pool joined into one proofs field (§7.1).

Every part of an Action MUST be a canonical encoding of its type, and *spendAuthSig* MUST be a valid signature, checked with *rk*, over the same SIGHASH_ALL hash as for a Spend, with a non-canonical *R* point rejected. The proof MUST verify under the verifying key *vk* for the circuit version in force: OrchardCircuitVersion::InsecurePreNU6_2 from NU5 up to NU6.2, FixedPostNU6_2 for NU6.2, and PostNu6_3 from NU6.3 onward. Finally, *rk* MUST NOT be the identity point.

Unlike in Sapling, *cv_net* may be the zero point, while *rk* and *epk* cannot be. The rule against *rk* being the identity point came in as a soft fork with no fixed activation height, from zcashd v6.12.1 and Zebra v4.3.1 (ZIP 256), after an *rk* encoding the zero point made both nodes panic during proof verification; the circuit itself supports the point, and excluding the point was the simpler and safer response. *nf* and *cm_x* are checked only to be integers below *q_P*, not to be x-coordinates of points on the Pallas curve.

## 4.4 Sending notes and dummy notes

To send Sprout value, a wallet builds a transaction with one or more JoinSplits (§4.7.1). The wallet first makes a new JoinSplit signing key pair, *joinSplitPrivKey* and *joinSplitPubKey*, for the whole transaction, and for each JoinSplit picks the random seed *randomSeed* and the notes to spend, which is enough to compute *h_sig*, and one more random value *φ* (phi).

For each of the two new notes, the wallet picks a random commitment trapdoor *rcm*, derives the note's *ρ* from *φ*, the note's index and *h_sig* with *PRF^ρ*, and computes the note commitment *cm* from the recipient's paying key *a_pk*, the amount *v* and *ρ*. The note plaintext holds the lead byte 0x00, *v*, *ρ*, *rcm* and the memo, and the wallet encrypts the two plaintexts to the recipients' transmission keys *pk_enc*, which gives *epk* and the two ciphertexts (§4.19). The wallet SHOULD shuffle the order of the spent notes and the order of the new notes to leak less information.

When all JoinSplits are complete, the wallet signs the transaction data given in §4.11 with *joinSplitPrivKey*, which gives *joinSplitSig*, and sends the transaction to the peer-to-peer network. Support for sending to Sprout addresses is OPTIONAL for any node or wallet, and from Canopy, ZIP 211 requires nodes and wallets to disable sending to Sprout addresses, a restriction user interfaces and API documentation SHOULD make clear.

To send value into the Sapling pool, a wallet builds a transaction with one or more Outputs (§4.7.2). The wallet first chooses the outgoing viewing key *ovk* able to decrypt the payment: the key of the address the payment comes from, the key of a whole account (ZIP 32), or none (⊥), which gives the sender forward secrecy of the payment against a later compromise of the sender's own secrets. The wallet also chooses the note plaintext lead byte by the rules of §3.2.1.

For each Output, given an amount *v* and the recipient's address (*d*, *pk_d*), the wallet checks that *pk_d* is a point of prime order on the Jubjub curve, computes the base point *g_d* from *d* and checks that *g_d* exists, and picks a random value commitment trapdoor *rcv*. With lead byte 0x01, the wallet picks a random non-zero *esk* and a random *rcm*, and the plaintext carries *rcm* itself; with lead byte 0x02, the wallet instead picks a 32-byte seed *rseed* and derives *rcm* and *esk* from *rseed* by hashing with the tags 4 and 5, and the plaintext carries *rseed*.

The wallet then computes the value commitment *cv* from *v* and *rcv*, and the note commitment *cm* from *g_d*, *pk_d*, *v* and *rcm*. The note plaintext holds the lead byte, *d*, *v*, *rcm* or *rseed*, and the memo, and the wallet encrypts the plaintext to *pk_d* with base *g_d* and to *ovk*, which gives *epk*, *C_enc* and *C_out*, with the encryption taking *esk* and using *cv* and *cm_u* to derive the outgoing cipher key (§4.20). Finally the wallet makes the proof for the Output statement (§4.18.3), and SHOULD shuffle the order of Outputs in the transaction to leak less information.

To send value into the Orchard or Ironwood pool, a wallet builds a transaction with one or more Actions, and for each Action the wallet makes the output side as follows, given an amount and the recipient's address, which is made of a diversifier *d* and a transmission key *pk_d* (§4.7.3). The wallet chooses *ovk* as for Sapling and the lead byte by §3.2.1 for the Action's pool, then checks that *pk_d* is a valid key, computes the address's base point *g_d* from the diversifier, and picks two random values: a trapdoor *rcv* for the value commitment, and a 32-byte seed *rseed*. The new note's *ρ* (rho) is set to the nullifier of the note spent in the same Action, so each new note gets a *ρ* no earlier note has used. From *rseed* and *ρ* the wallet then derives three more values, each by hashing with a different one-byte tag: the ephemeral key *esk* used for encryption, the nullifier randomness *ψ* (psi), and the commitment trapdoor *rcm*.

For Ironwood notes the hash for *rcm* also covers the address, the amount, *ρ* and *ψ*. If *esk* comes out as zero, or the note commitment below cannot be computed, the wallet starts again with a new *rseed*. With these values the wallet computes the value commitment *cv_net*, which hides the spent note's value minus the new note's value, and the note commitment *cm_x*, which covers the address, the amount, *ρ* and *ψ*. The note plaintext holds the lead byte, the diversifier, the amount, *rseed* and the memo, and only *rseed* travels, with the recipient recomputing *ψ* and *rcm* from *rseed*.

The wallet encrypts the plaintext twice: to the recipient's *pk_d*, so the recipient can read the note, and to the sender's outgoing viewing key, so the sender can read the note later (§4.20). Finally the wallet fills in the spending side of the Action and makes the proof for the Action statement (§4.18.4). When an Action has no real note to spend, the wallet SHOULD spend a dummy note (§4.8.3) and use the dummy note's nullifier as *ρ*, and the wallet SHOULD shuffle the order of Actions within each pool to leak less about the transaction. The one-byte tags for *esk* and *rcm* are swapped relative to Sapling, which the original notes was an oversight with no reason behind the swap.

A JoinSplit always has room for exactly two spent notes and two new notes, and a wallet which needs fewer fills the empty places with dummy notes (§4.8.1). For a dummy spent note, the wallet makes a new random spending key *a_sk*, derives the paying key *a_pk*, sets the value to zero, picks *ρ* and *rcm* at random, and computes the nullifier *nf* from *a_sk* and *ρ*. The Merkle path of the dummy note can be any path, because the wallet sets *enforceMerklePath* to 0 for the note when making the proof, and a dummy new note is made as normal, with zero value and a random shielded address as recipient.

Sapling has no fixed places to fill, but dummy spent notes can still hide how many real notes a transaction spends from the Sapling pool (§4.8.2). For a dummy spent note with lead byte 0x02, the wallet picks a random spending key *sk*, derives *ak*, *nk* and an address (*d*, *pk_d*) from *sk*, sets the value *v* and the tree position *pos* to zero, picks *rcv* and *rseed* at random, and derives *rcm* from *rseed* as for a real note. The wallet then computes *cv* and *cm*, derives *ρ* by hashing *cm* with *pos*, and computes *nf* from *nk* and *ρ*; the Merkle path can be any path, because the Spend statement does not check the path of a note with value zero, and a dummy new note is made as in Sprout.

Dummy spent notes can hide the number of real spends from the Orchard pool in the same way (§4.8.3). For the spending side of an Action with a dummy note, the wallet picks a random spending key *sk*, derives a full viewing key (*ak*, *nk*, *rivk*) and an address (*d*, *pk_d*) from *sk*, sets *v* to zero, picks *rseed* at random, and sets *ρ* to the x-coordinate of a random Pallas point. From *rseed* and *ρ* the wallet derives *ψ* and *rcm* as for a real Orchard note, computes the note commitment *cm*, starting again with a new *rseed* if *cm* cannot be computed, and computes the nullifier *nf* from *nk*, *ρ*, *ψ* and *cm* (§4.16); the Merkle path can be any path, because the Action statement does not check the path of a note with value zero.

From NU6.3, two changes apply to an Action with *enableCrossAddress* set to 0. If the new note of the Action is a real note, the dummy spent note uses the full viewing key and address of the new note's recipient in place of new ones, and *spendAuthSig* is made with the matching spend authorizing key *ask*. A dummy new note normally has zero value and a random address, but in such an Action the dummy new note goes to the expanded receiver of the spent note, and if the spent note is real, the dummy new note's ciphertext is random bytes in place of an encryption of the note (ZIP 326).

## 4.5 Merkle paths

Each shielded pool keeps the note commitments of the pool in a Merkle tree of its own, and the rules below apply to each tree separately (§4.9). The Sprout tree has depth 29, the Sapling and Orchard trees have depth 32, and each protocol has its own node hash *MerkleCRH*. Layer *h* of a tree, counting from layer 0 at the root, has 2^*h* nodes numbered from 0, and each node holds a hash value.

The nodes of the deepest layer are the leaves. Each new note commitment takes the next free leaf, and each leaf not yet used holds a fixed value *Uncommitted*; for Sprout the original assumes nobody can find a note whose commitment equals *Uncommitted*, while Sapling and Orchard need no such assumption, because their *Uncommitted* value can never be a note commitment. Each node above the leaves holds the *MerkleCRH* hash of the node's layer number and the hashes of the node's two children.

The Merkle path of a leaf is the list of hashes of the sibling nodes on the way from the leaf up to the root, one for each layer from the leaf layer up to layer 1, where the sibling at a layer is the other child of the same parent as the leaf's ancestor at the layer. With the path, anyone can recompute the root *rt* from the leaf and so check the leaf is in the tree with the root.

Sapling hash values are bit sequences, but the Spend proof takes the root *rt* as a field element, and the Spend circuit accepts non-canonical encodings of the inputs to *MerkleCRH* at each node; Orchard hash values are integers below *q_P*, and the Action circuit accepts non-canonical inputs in the same way. The Action circuit may also let the path check pass when any hash on the path, the root included, is 0, which can happen only when *SinsemillaHash* fails and returns ⊥, and the original allows the case to match the incomplete addition the circuit uses for Sinsemilla. A failure of *SinsemillaHash* gives a non-trivial discrete-logarithm relation (Theorem 5.4.4), assumed infeasible to find, and on the same ground the original argues that letting an adversary pass the check in the case is safe.

## 4.6 Signatures and balance

Zcash binds every signature and proof that authorizes spending to the transaction the signature or proof belongs to, which stops anyone from replaying them in a different transaction (§4.10). The wallet hashes the transaction, together with the specific input in the case of a transparent input, into a SIGHASH transaction hash *SigHash*, and although transparent inputs, Sprout JoinSplits, Sapling Spends and Orchard Actions are each authorized differently, one transaction version always uses one SIGHASH algorithm. The binding also counters malleability: the BCTV14, Groth16 and Halo 2 proofs are malleable, meaning someone who does not know all the auxiliary inputs of a proof can still turn the proof into a new proof with related auxiliary inputs.

Bitcoin defines several SIGHASH types, each covering different parts of a transaction, and all Zcash-specific signatures use *SIGHASH_ALL*: the JoinSplit signature, the spend authorization signatures, and the Sapling and Orchard binding signatures, whose hashes are not tied to any transparent input and leave out every *scriptSig* field. Every SIGHASH type also covers *nJoinSplit*, *vJoinSplit* and, when present, *joinSplitPubKey*, but never *joinSplitSig*, and covers the fields added by Overwinter, Sapling and NU5 once each upgrade is active.

Overwinter replaced Bitcoin's original algorithm to fix the deficiencies described in ZIP 143. Version 1 and 2 transactions use the algorithm of ZIP 76, which is still to be written, and versions 3, 4, 5 and 6 use ZIP 143, ZIP 243, ZIP 244 and ZIP 229 respectively. From NU5 onward, a SIGHASH type encoding in a version 5 or 6 transaction must be canonical, one of 0x01, 0x02, 0x03, 0x81, 0x82 or 0x83, whereas earlier versions ignored undefined bits, and during each upgrade era, from Overwinter to NU7, every transaction must use the consensus branch ID of the active upgrade. A transaction with Orchard Actions must be version 5 or 6, and a transaction with Ironwood Actions must be version 6; versions 5 and 6 also give nonmalleable transaction identifiers, and a wallet may use them for that reason alone.

In Sprout, each transaction gets a fresh, single-use JoinSplitSig key pair (§4.11). The wallet signs *dataToBeSigned*, the *SIGHASH_ALL* hash of the whole transaction, with the private key, and places the public key in the transaction as *joinSplitPubKey*, and the signature *joinSplitSig* binds every JoinSplit description to the transparent values *vpub_old* and *vpub_new* and to the other JoinSplits in the transaction. A transaction with no JoinSplits omits both *joinSplitPubKey* and *joinSplitSig*, and any other transaction is valid only if *joinSplitSig* verifies on *dataToBeSigned* under *joinSplitPubKey*.

The single-use key must also be tied to the owners of the spent notes. For each input *i*, the creator computes *h_i* = PRF^pk with key *a_sk* applied to (*i*, *h_sig*), from the input's spending key *a_sk* and from *h_sig*, which depends on *joinSplitPubKey*, and the JoinSplit statement proves each *h_i* correct, which shows the holders of every *a_sk* authorized the *joinSplitPubKey* key to sign the transaction.

Balance in Sprout follows Bitcoin, where transparent outputs must not exceed transparent inputs and the difference goes to the miner as part of the coinbase (§4.12). Each JoinSplit counts as both an input and an output of the transparent transaction value pool: *vpub_old* takes value out of the pool into the shielded notes and counts as an output, while *vpub_new* brings value back and counts as an input. Unlike Zerocash, Zcash has no separate Mint and Pour operations, because *vpub_old* covers both, and a different number of real input notes does not by itself make two JoinSplits distinguishable. At least one of *vpub_old* and *vpub_new* must be zero, which loses no generality, because the smaller of the two can be subtracted from both, and which avoids differences between transactions made by different client implementations.

In Sapling, the Sapling balancing value *v^balanceSapling* is the value of the Spends minus the value of the Outputs, a signed number of zatoshi carried in the field *valueBalanceSapling* (§4.13). A version 4 transaction always includes the field, and a version 5 transaction treats the value as zero when there are no Spends or Outputs. A positive *valueBalanceSapling* moves value from the Sapling chain value pool into the transparent transaction value pool and counts as an input, and a negative value moves value the other way and counts as an output.

The amounts are hidden inside the value commitments *cv*, so validators cannot add them up directly; instead, a Sapling binding signature *bindingSigSapling* shows the hidden amounts balance. The same signature also proves the signer knew the commitment trapdoors *rcv*, which stops an attacker from replaying the Output descriptions in another transaction, while the Spend descriptions are already protected by their spend authorization signatures.

The key pair of the binding signature is not random, and comes from the commitments themselves. Each validator computes the validating key *bvk* by adding the Spend commitments, subtracting the Output commitments, and subtracting a commitment to *v^balanceSapling* with zero trapdoor:

*bvk* = Σ *cv^old* − Σ *cv^new* − ValueCommit_0(*v^balanceSapling*).

The transaction does not include *bvk*, and every validator recomputes the key. The signer, who knows every trapdoor, computes the signing key *bsk* = Σ *rcv^old* − Σ *rcv^new*, SHOULD confirm that *bsk* derives *bvk* to catch implementation faults, and signs *SigHash*, the *SIGHASH_ALL* hash for the transaction's version; validators accept only if *bindingSigSapling* verifies under *bvk*.

The check works because each commitment is *v*·V + *rcv*·R for two fixed bases V and R, so the sum above equals *v\**·V + *bsk*·R, where *v\** = Σ *v^old* − Σ *v^new* − *v^balanceSapling*. A valid signature proves the signer knows *bsk* with *bvk* = *bsk*·R, which is an opening of *bvk* to the value 0, and if *v\** were not zero modulo the group order, the signer would hold two openings of *bvk* to different values, which breaks the binding property of the commitments, while Groth16 knowledge soundness ensures the proofs could not exist without the trapdoors.

The group arithmetic shows only that *v\** is zero modulo the group order, so the specification also bounds *v\**: the Spend and Output statements limit every note value to 64 bits, *valueBalanceSapling* is a signed 64-bit integer, and the 2 MB transaction limit allows at most 5681 Spends and 2109 Outputs, which keeps *v\** far inside the range where no wrap-around can occur, so *v\** is exactly zero. The binding signature thus proves that Spends and Outputs balance without revealing any amount, and that a signer knowing the sum of the trapdoors authorized *SigHash*. A spender MAY show any strict subset of the trapdoors to parties helping to build the transaction, but showing all of them could let someone replay the Outputs; the same technique appears in Mimblewimble, where *bsk* is a "synthetic blinding factor", and in Bulletproofs.

Orchard uses the same mechanism with Actions, each of which may spend one note and may create one note (§4.14). The Orchard balancing value *v^balanceOrchard*, in the field *valueBalanceOrchard*, is the net value spent by the Orchard Actions, and from NU6.3 the Ironwood pool has its own *v^balanceIronwood* in *valueBalanceIronwood*, with every rule below applying to each pool separately. The value is zero when the pool has no Actions, and follows the same sign convention as Sapling.

Each Action commits to its net value, spent minus created, in *cv^net*, so validators compute *bvk* = Σ *cv^net* − ValueCommit_0(*v^balance*), and the signer computes *bsk* = Σ *rcv^net* and SHOULD confirm that *bsk* derives *bvk*. The signer signs *SigHash*, the version 5 (ZIP 244) or version 6 (ZIP 229) hash, and validators accept only if *bindingSigOrchard* verifies under *bvk*; replay protection matters less here, because every Action already carries a spend authorization signature, but the binding signature still proves knowledge of the trapdoors.

The security argument matches Sapling's, with Halo 2 knowledge soundness in place of Groth16. For the bound, the Action statement limits each net value to the range from −(2^64−1) to 2^64−1, the balancing value is a signed 64-bit integer, and a consensus rule allows at most 2^16−1 Actions, which keeps the sum inside the range where no wrap-around can occur. Checking the binding signature therefore proves the Actions balance without revealing any net value, and a spender MAY share any strict subset of the trapdoors with cooperating parties.

A spend authorization signature proves the spender holds the spending key of each spent note, in both Sapling (*SpendAuthSig^Sapling*, on Jubjub) and Orchard (*SpendAuthSig^Orchard*, on Pallas) (§4.15). The proof itself could have carried the check, as the Sprout JoinSplit statement does, but a separate signature lets a device with little memory or computing power, such as a hardware wallet, authorize a spend without building or verifying the proof. Validators need the signature's validating key, and the key must not link the transaction to the address or the spending key, so Zcash uses a rerandomizable signature scheme: the Spend or Action statement proves the published key *rk* is a rerandomization of the authorization validating key *ak* with a randomizer the signer knows, and the signature covers *SigHash*, so no one can replay the signature elsewhere.

For each Spend or Action, the signer chooses a fresh random randomizer *α*, derives the randomized signing key *rsk* from *α* and the spend authorizing key *ask*, and derives *rk* from *rsk*. The signer then builds the proof *π* with *α* as a private input and *rk* as a public input, and signs *SigHash* with *rsk* to give *spendAuthSig*, and the transaction carries *spendAuthSig* and *π* in the Spend description, or in the *vSpendAuthSigsSapling*, *vSpendAuthSigsOrchard* or *vSpendAuthSigsIronwood* field of a version 5 or 6 transaction.

A device with limited memory or computing power MAY hand the proof step, and only the proof step, to a helper. The helper then learns *ak* and the proof authorizing key *nsk*, from which the nullifier key *nk* follows (in Orchard the helper needs *nk* directly), which is enough to recognize the spender's spent notes and to recognize and decrypt incoming notes, but the helper still cannot spend, because the helper cannot produce a spend authorization signature.

## 4.7 Nullifiers and pool balances

Each note has a value *ρ* (rho) which makes the note unique, and the note's nullifier *nf* is computed from *ρ* (§4.16). In Sprout, Orchard and Ironwood, *ρ* is a field of the note itself, while in Sapling, *ρ* belongs to the note at the note's position *pos* in the commitment tree, and is computed by mixing the note commitment *cm* with the position, *ρ* = MixingPedersenHash(*cm*, *pos*). A Sprout nullifier is *PRF^nf* of *ρ*, keyed by the note's spending key *a_sk*, and a Sapling nullifier is *PRF^nf* of the encoding of *ρ*, keyed by the encoding of the nullifier deriving key *nk*.

An Orchard or Ironwood nullifier takes more steps: the wallet adds PRF^nf_nk(*ρ*) to the note's value *ψ* (psi) modulo the base-field size *q_P*, multiplies a fixed Pallas point *K* by the sum, adds the note commitment *cm*, and keeps the x-coordinate:

*nf* = Extract_P([(PRF^nf_nk(*ρ*) + *ψ*) mod q_P]·*K* + *cm*).

The reduction modulo *q_P* is intended, even though Pallas scalars are taken modulo *r_P*, and the *ρ* and *ψ* used must always match the note *cm* commits to.

Every pool's nullifier derivation must meet three security requirements. The note's fields, and in Sapling the note's position, must fully determine the nullifier, in a way the JoinSplit, Spend or Action statement can check; as long as *ρ* values are unique, two notes with different commitments must never share a nullifier; and an adversary must not be able to link nullifiers to unknown notes better than by chance, even with the notes' incoming viewing keys (but not their full viewing keys), and even if the adversary created the notes.

Each chain value pool has a balance, the value the pool holds in the block chain up to a given height (§4.17). The transparent balance is the sum of all unspent transaction outputs, the Sprout balance is the sum of every *vpub_old* minus the sum of every *vpub_new* (ZIP 209), and the Sapling, Orchard and Ironwood balances are each the negation of the sum of every *valueBalanceSapling*, *valueBalanceOrchard* or *valueBalanceIronwood* respectively.

The deferred development fund pool balance is the sum, over all heights, of *totalDeferredOutput* minus *totalDeferredInput* (ZIP 207), where *totalDeferredOutput* is zero before NU6 and *totalDeferredInput* is zero before NU6.1. For each of these six pools a consensus rule applies: if accepting a block would make the pool's balance negative, all nodes MUST reject the block as invalid.

From NU7, the Network Sustainability Mechanism (ZIP 237) tracks value removed from circulation and later reissued through the block subsidy. The value removed at a height, *NSMValueRemoved*, equals *NSMFeeContribution*, the part of transaction fees set aside by ZIP 235, which is the only removal mechanism in NU7. The NSM Value Balance is zero before the block just below the NU7 activation height, starts at the constant INITIAL_NSM_VALUE_BALANCE at the block, and at each later height loses the block's *AdditionalBlockSubsidy* and gains the block's *NSMValueRemoved*, and if accepting a block would make the NSM Value Balance negative, all nodes MUST reject the block.

The NSM Value Balance is consensus state kept beside the pools, but no one can spend from the NSM Value Balance and the total issued supply does not include the balance, which counts ZEC not in circulation; reissuance moves value from the NSM Value Balance into the issued supply through the block subsidy. As ZIP 2003 clarifies, the Sprout balance at NU7 activation remains issued and counts toward the issued supply. The total issued supply *IssuedSupply* is the sum of the transparent, Sprout, Sapling, Orchard, deferred and Ironwood pool balances, and if accepting a block would make the total issued supply, computed without overflow, greater than MAX_MONEY zatoshi, all nodes MUST reject the block as invalid.

## 4.8 What the proofs prove

Each shielded transfer carries a zero-knowledge proof of a fixed statement (§4.18). The verifier sees only the public values, called the primary input, which also appear in the transaction, while the prover knows further secret values, called the auxiliary input, and the proof shows the secret values exist and satisfy every named condition of the statement without revealing them. There are four statements: the JoinSplit statement for Sprout, the Spend and Output statements for Sapling, and the Action statement for Orchard.

For the JoinSplit statement (§4.18.1), the public values are the anchor *rt*, the nullifiers *nf^old* of the two spent notes, the commitments *cm^new* of the two new notes, the values *vpub_old* and *vpub_new*, the hash *h_Sig*, and one tag *h_i* per spent note. The secret values are each old note's Merkle path and position, the old notes, each a key *a_pk*, a value *v*, a *ρ* and a trapdoor *rcm*, the spending keys *a_sk* of the old notes, the new notes, a random seed *φ*, and one bit *enforceMerklePath_i* per old note. *Merkle path validity* says that wherever *enforceMerklePath_i* is 1, the path leads from the old note's commitment to *rt*, and *Merkle path enforcement* says any old note with a nonzero value must have *enforceMerklePath_i* set to 1, so only a zero-value note can skip the path check.

*Balance* says *vpub_old* plus the old note values equals *vpub_new* plus the new note values, with the total within the value range. *Nullifier integrity* says each *nf^old_i* is PRF^nf of *ρ^old_i* under *a_sk*, and *spend authority* says each old note's *a_pk* is PRF^addr of 0 under *a_sk*, so the prover holds the spending key of each spent note. *Non-malleability* binds each *h_i* to *a_sk*, the index *i* and *h_Sig* through PRF^pk, *uniqueness of ρ^new* says each new note's *ρ* is PRF^ρ of *i* and *h_Sig* under the seed *φ*, and *note commitment integrity* says each *cm^new_i* is the commitment of the new note.

For the Spend statement (§4.18.2), the public values are the anchor *rt*, the value commitment *cv*, the nullifier *nf* and the randomized validating key *rk*. The secret values are the Merkle path and position, the note's base point *g_d* and transmission key *pk_d*, the value *v*, the value trapdoor *rcv*, the note commitment *cm* as a point with its trapdoor *rcm*, the randomizer *α*, the spend validating key *ak*, and the nullifier private key *nsk*. *Note commitment integrity* says *cm* commits to *g_d*, *pk_d* and *v* under *rcm*; *Merkle path validity* says either *v* = 0 or the path leads from *cm_u*, the u-coordinate of *cm*, to *rt*, so a zero-value note needs no valid path; *value commitment integrity* says *cv* commits to *v* under *rcv*; and the *small order checks* say neither *g_d* nor *ak* is a point of small order.

*Nullifier integrity* says *nf* is PRF^nf keyed by *nk* = [*nsk*]ℋ and applied to *ρ*, where *ρ* is a mixing Pedersen hash of *cm* and the note position. *Spend authority* says *rk* is *ak* randomized by *α*, that is, *ak* + [*α*]𝒢, and *diversified address integrity* says *pk_d* = [*ivk*]*g_d*, where *ivk* is CRH^ivk of *ak* and *nk*, and together the three conditions tie the note's address to the same *ak* and *nsk* that produce *nf* and *rk*.

The original also lists what the Spend circuit does not check. Every input must be constrained to its stated type, and *cv* and *rk* are curve points; each Merkle layer does not check that its input bits are the canonical encoding of the previous layer's output; the circuit does not check *rk* for small order, which §4.4 checks outside the statement; and the circuit does not check that *rcv* or *rcm* is less than the group order *r_J*.

For the Output statement (§4.18.3), the public values are the value commitment *cv*, the note commitment's u-coordinate *cm_u*, and the ephemeral key *epk*, and the secret values are *g_d*, the transmission key encoding *pk⋆_d* as a bit string, the value *v*, the trapdoors *rcv* and *rcm*, and the ephemeral secret key *esk*. *Note commitment integrity* says *cm_u* comes from the commitment to *g_d*, *pk⋆_d* and *v* under *rcm*, *value commitment integrity* says *cv* commits to *v* under *rcv*, the *small order check* says *g_d* is not of small order, and *ephemeral public key integrity* says *epk* = [*esk*]*g_d*. The circuit does not check that *pk⋆_d* encodes a valid point, which is why the original types *pk⋆_d* as bits, and does not check that the trapdoors are less than *r_J*.

For the Action statement (§4.18.4), one Action spends one note and creates one note. The public values are the anchor *rt*, the net value commitment *cv^net*, the old note's nullifier *nf^old*, *rk*, the new note commitment's x-coordinate *cm_x*, the flags *enableSpends* and *enableOutputs*, and from NU6.3 also *disableCrossAddress*; §4.6 uses the same statement for Ironwood Actions, with the Ironwood pool's anchor, and sets *disableCrossAddress* to 1 − *enableCrossAddress*. The secret values are the Merkle path and position; the old note's *g_d*, *pk_d*, value *v^old*, *ρ^old*, *ψ^old*, *rcm^old* and commitment *cm^old*; the randomizer *α*, the validating key *ak*, the nullifier key *nk* and the trapdoor *rivk*; the new note's *g_d*, *pk_d*, value *v^new*, *ψ^new* and *rcm^new*; and the value trapdoor *rcv*.

*Old note commitment integrity* says the commitment to the old note's fields is either *cm^old* or ⊥, and *Merkle path validity* says either *v^old* = 0 or the path leads from the x-coordinate of *cm^old* to *rt*. *Value commitment integrity* says *cv^net* commits to the difference *v^old* − *v^new* under *rcv*, *nullifier integrity* says *nf^old* = DeriveNullifier_nk(*ρ^old*, *ψ^old*, *cm^old*), and *spend authority* says *rk* = *ak* + [*α*]𝒢. *Diversified address integrity* says either *ivk* is ⊥, or *pk_d^old* = [*ivk*]*g_d^old*, where *ivk* is Commit^ivk of the x-coordinate of *ak* and *nk* under *rivk*.

*New note commitment integrity* says the x-coordinate of the new note's commitment is *cm_x* or ⊥, where the new note's *ρ* is *nf^old* reduced modulo *q_P*, so the new note takes the new note's *ρ* from the nullifier of the note spent in the same Action. The *enable spend flag* condition says *v^old* = 0 or *enableSpends* = 1, and the *enable output flag* condition says *v^new* = 0 or *enableOutputs* = 1, so with a flag at 0 the Action can still carry a zero-value dummy note on the flagged side. From NU6.3, the *cross-address restriction* says either *disableCrossAddress* = 0, or the new note has the same *g_d* and *pk_d* as the old note.

The ⊥ cases model the circuit's use of incomplete point addition in Sinsemilla, and a ⊥ result from NoteCommit or Commit^ivk satisfies the matching check. Theorem 5.4.4 shows that reaching an exceptional case gives a nontrivial discrete-log relation on Pallas, which is infeasible to find if discrete logarithms are hard, and on the same grounds §4.9 allows a Merkle check to pass when any hash on the path outputs 0.

The Action circuit does not check that each Merkle layer's input is canonical, that the trapdoors *rcv*, *rcm^old* and *rcm^new* are less than *r_P*, that the encodings of the *g_d* and *pk_d* values are valid, or that *rt* and *cm_x* are Pallas x-coordinates or 0. Every input must be constrained to its type, which means the *g_d* and *pk_d* values and *ak* are nonzero points, and *rk* is never the identity point, because §4.6 rejects the case. The scalar multiplication inside ValueCommit must work over the whole range of *v^old* − *v^new*, which differs from the range of the transaction's balance value.

Where a field element is used as a scalar, the circuit decomposes the scalar into bits or windows, and the decomposition MUST be canonical unless an equivalent statement can be proved. The equivalence holds for *rcm*, *rcv*, *rivk* and *α*, because the statement only proves knowledge of those scalars, while the scalar in DeriveNullifier must be canonical to avoid a double-spend vulnerability, and the same applies to *ivk*.

The prover may witness *ak* with either sign bit (ỹ = 0 or 1), although key generation always gives ỹ = 0, and the original calls the choice harmless, because the signers then know the spending key up to sign. The Action statement has no equivalent of the Sapling *epk* check on purpose, because the ZIP 212 checks, required since before NU5, prevent the attack the *epk* check addressed. A soundness bug in the scalar multiplication of the circuit before NU6.2 could have allowed a balance violation; the statement was correct throughout, and the corrected NU6.2 circuit has a verifying key of its own, chosen by a rule in §4.6.

## 4.9 Encrypting and finding notes

Every shielded output carries an encrypted copy of the note's plaintext, which the sender writes into the transaction and only the holder of the right viewing key can open (§4.19, §4.20). The same encrypted copies let a wallet find its own notes by trial-decrypting every output on the block chain, and then learn which of those notes are spent by watching for their nullifiers (§4.21, §4.22). The design rationale is in §8.7.

A Sprout recipient needs the value *v*, the value *ρ* and the commitment trapdoor *rcm*, together with a 512-byte memo, and the sender encrypts these to the recipient's transmission key *pk_enc* (§4.19). One JoinSplit description has a single ephemeral key pair (*epk*, *esk*), which all its new outputs share. For each output *i*, the sender agrees a *sharedSecret_i* from *esk* and the recipient's *pk_enc,i*, derives a symmetric key *K^enc_i* from the output index *i*, the JoinSplit's *h_Sig*, *sharedSecret_i*, *epk* and *pk_enc,i*, and encrypts the raw note plaintext *np_i* to give *C^enc_i*, and the transmitted notes ciphertext is *epk* followed by all the *C^enc_i* (§4.19.1).

The Sprout recipient holds the incoming viewing key *ivk* = (*a_pk*, *sk_enc*), and for each output repeats the key agreement from the recipient's side, using *sk_enc* with *epk* and the recipient's own *pk_enc* in the key derivation (§4.19.2). Decryption returns failure (⊥) when the symmetric decryption fails, when the plaintext's *leadByte* is not 0x00, or when the note *n* = (*a_pk*, *v*, *ρ*, *rcm*) rebuilt from the plaintext does not commit to the output's note commitment *cm_i*, and otherwise gives the note and the note's memo. Knowing a note was received does not say whether the note is spent: the recipient also needs the spending key *a_sk* to compute the nullifier *nf*, and the note is unspent exactly when *nf* is not in the chain's nullifier set.

A Sapling, Orchard or Ironwood recipient needs the diversifier *d*, the value *v* and the 32-byte seed *rseed* (before Canopy, *rcm* itself), together with the memo, and the sender encrypts these to the diversified transmission key *pk_d*, which the recipient opens with the private key *ivk* (§4.20). Unlike Sprout, every output note has a fresh ephemeral key of its own, and one description covers both pools, with Sapling working over the Jubjub curve and Orchard over the Pallas curve, and Ironwood-pool notes using the Orchard protocol.

Encryption happens only while sending a note (§4.7.2, §4.7.3), when the address's base point *g_d* is known to be valid and the ephemeral private key *esk* has already been chosen (§4.20.1). The sender computes the ephemeral public key *epk* = [*esk*]*g_d* and encodes the key as the field *ephemeralKey*, agrees a *sharedSecret* from *esk* and *pk_d*, derives *K^enc* from *sharedSecret* and *ephemeralKey*, and encrypts the note plaintext *np* = (*leadByte*, *d*, *v*, *rseed*, *memo*) to give *C^enc*.

The sender also writes a second, shorter ciphertext *C^out*, which lets the holder of an outgoing viewing key *ovk* recover what was sent. The *ovk* is the sending address's outgoing viewing key, a key belonging to a ZIP 32 account, or ⊥ for no recovery. With a real *ovk*, the outgoing cipher key *ock* is PRF^ock keyed by *ovk* over the value commitment *cv*, the extracted note commitment *cm\** and *ephemeralKey*, and the outgoing plaintext *op* is the encoding of *pk_d* followed by *esk*; with *ovk* = ⊥, the sender picks *ock* and *op* at random instead. Either way, *C^out* is the encryption of *op* under *ock*, and the transmitted note ciphertext is (*ephemeralKey*, *C^enc*, *C^out*); for Orchard, *cv* also depends on the value of the note spent in the same Action.

In both Sprout and Sapling or Orchard, a sender may replace *C^enc* with a random, undecryptable dummy and deliver the note out-of-band (§4.19.1, §4.20.1). The ephemeral key MUST still be a random public key rather than random bits, and the specification does not address how a recipient validates a note received this way.

The recipient tries every output with *ivk*, using the output's *cm\**, the cmu field for Sapling or the cmx field for Orchard (§4.20.2). The pool, the containing block's *height* and the transaction version *txVersion* select the allowed lead bytes, and the procedure returns ⊥ at the first of these failures:

1. *ephemeralKey* does not decode to a point *epk*.
2. The symmetric decryption of *C^enc*, under the *K^enc* derived from *sharedSecret* = [*ivk*]*epk*, fails.
3. *leadByte* is not in allowedLeadBytes for the pool, *height* and *txVersion*.
4. For Sapling, *d* gives no valid *g_d*.
5. From Canopy onward, when *leadByte* is not 0x01, the *esk* derived from *rseed* (and, for Orchard, from *ρ*) does not reproduce the received *ephemeralKey*.
6. The derived *rcm* is not below the group order *r_G*.
7. For Orchard or Ironwood, the note commitment cannot be computed.
8. The recomputed note commitment does not match *cm\**.

The allowed lead bytes (§3.2.1) carry the ZIP 212 grace period: before Canopy only 0x01 is allowed, during the first ZIP212GracePeriod blocks after Canopy activation both 0x01 and 0x02 are allowed, and after the grace period 0x02 is allowed in the Sapling and Orchard pools and 0x03 in the Ironwood pool. A 0x01 note therefore carries *rcm* directly and skips the *esk* check in step 5.

For Orchard, *ρ* is the nullifier *nf^old* of the note spent in the same Action, and the recipient derives *ψ* from *rseed* and *ρ*, and *rcm* from *rseed* and *leadByte* (for Orchard, also from *g_d*, *pk_d*, *v*, *ρ* and *ψ*). The recipient computes *pk_d* as [*ivk*]*g_d*, and the rebuilt note is (*d*, *pk_d*, *v*, *rcm*) for Sapling, or (*d*, *pk_d*, *v*, *ρ*, *ψ*, *rcm*) for Orchard or Ironwood.

Jubjub decoding accepts non-canonical point encodings, so an implementation MUST use the original *ephemeralKey* bytes from the transaction, not a re-encoding of *epk*, both in the key derivation and in the comparison of step 5, and Orchard specifies the same. From NU5, the §4.6 consensus rule makes every Action's *ephemeralKey* a valid nonzero Pallas point, so *epk* is never the identity. The domain separators [4] and [5] used to expand *rseed* are swapped between Orchard and Sapling, which the specification calls an oversight with no good reason behind the swap.

Normally a wallet decrypts only transactions in blocks, so a received Sapling note already has a position and the note's *ρ* can be computed (§4.16). Spent status needs the nullifier deriving key *nk*: a note is unspent exactly when the note's nullifier is not in the chain's nullifier set. A note can become spent as the node's best valid chain grows, and a reorganization can switch the node to a chain which does not contain the note's output at all. A client MAY decrypt a mempool transaction, using the next block height for *height*, but MUST NOT assume the transaction will be mined, and MUST treat the decrypted information as provisional and private.

The holder of *ovk* can open an output only if the sender used the *ovk* and not ⊥ (§4.20.3). The holder recomputes *ock* from *ovk*, *cv*, *cm\** and *ephemeralKey* and decrypts *C^out* to get *op*, and the procedure returns ⊥ if the decryption fails, if the *esk* in *op* is not below *r_G*, if the *pk_d* in *op* does not decode, if a Sapling *pk_d* is not in the prime-order subgroup, or if *pk_d* does not re-encode to the same bytes. The holder then agrees *sharedSecret* from *esk* and *pk_d*, decrypts *C^enc*, and applies the same lead-byte, diversifier, *rcm* and note-commitment checks as the *ivk* procedure.

The *ovk* procedure differs from the *ivk* procedure in three places: *pk_d* comes from *op* instead of [*ivk*]*g_d*; from Canopy onward, when *leadByte* is not 0x01, the *esk* derived from *rseed* MUST equal the *esk* from *op*; and the check that [*esk*]*g_d* re-encodes to *ephemeralKey* is unconditional and uses the *esk* from *op*. The original *ephemeralKey* bytes MUST again be used, here as input to PRF^ock and the key derivation and in the last comparison, and the remarks on *ρ*, spent status and the mempool apply to this procedure too.

For Sapling, the canonical-encoding check on *pk_d* is technically redundant with the subgroup check, because only small-order Jubjub points have non-canonical encodings, and an Orchard *pk_d* cannot be non-canonical. An earlier version of the specification lacked the subgroup check, and the current rule matches librustzcash, which zcashd has used for wallets since v2.1.2 and Zebra has always used. zcashd's separate consensus path, under which a shielded coinbase output must decrypt with the all-zero *ovk*, gained the check in v5.5.0 as a soft fork at height 2121200 on Mainnet and Testnet, a fork later found to be valid retrospectively, after which zcashd used librustzcash everywhere. Current zcashd and Zebra enforce the check retrospectively for consensus, and current zcashd enforces the check for wallet rescans, but older zcashd could accept a note whose *pk_d* in *C^out* encoded the identity point.

A Sprout wallet with spending key *a_sk* keeps three structures: a set of received notes with memos, a set of spent notes, and a map from nullifiers to notes (§4.21). For each JoinSplit description in each transaction, the wallet tries to decrypt every output with *ivk*, and on success records the note and memo, computes the note's nullifier with *a_sk*, and adds the nullifier to the map; any of the JoinSplit's spent nullifiers found in the map then marks the matching note as spent. At the end, the wallet has every note sent to the address, the note's memo, and whether the note is spent.

Sapling and Orchard scanning works the same way but needs only *nk* and *ivk*, typically taken from a full viewing key, and no spending key (§4.22). The wallet decrypts every Output or Action description with *ivk*, computes each nullifier with *nk* (a Sapling note also needs the note's position *pos*), and checks the nullifiers of every Spend and Action description against the map. The scan does not use *ovk* or *C^out*, which a full scan does not need; *ovk* is useful because a single transaction is enough to recover what the transaction sent, and in a partial scan, decrypting *C^out* can reveal notes spent inside the scanned range but received before the range. A scan cannot find notes sent out-of-band or with incorrect ciphertexts, and the wallet can see such a note spent only if the wallet already knows the note's nullifier.
